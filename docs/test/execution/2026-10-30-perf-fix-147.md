## 5. 观测与证据完整性说明

- **慢 SQL**：`restore.sh` 每档开启 `slow_query_log=ON, long_query_time=0.1`。
  但快照协议每档 `down -v` 重建数据卷，前几档的慢日志随卷销毁，仅最后一档（attachment-1）
  的日志留存：头部 + 两条 `COMMIT` 群组提交等待（Query_time 0.141s、Rows_examined 0），
  无任何实际 SQL 超 100ms——与基线轮「零慢 SQL」口径一致。协议改进项：取证应在每档收尾时
  `docker compose cp` 拷出当日慢日志（基线轮即如此执行，本轮脚本漏了这一步）。
- **GC 日志**：本轮未注入 `compose.override.yaml` 的 GC 取证（基线轮已证 G1 占墙钟 1.3%、
  非瓶颈；本轮无内存类异常迹象：无 HeapDump、无容器重启）。
- **docker stats**：各档 ~1Hz 采样在证据 `stats-*.csv.gz`（service-oa / mysql CPU 未打满，
  10 vCPU VM 下与基线同形态）。
- **行数**：收尾 `oa_process=10001` 与快照一致（最后一档 attachment 不写流程实例，
  每档恢复快照后写入的实例随下一次 down -v 清除）。
- k6 侧零阈值违反（全部 `✓`，无 `✗`）；冒烟档 8/8 动作 100% 成功。
