## 1. 修复机制（EXPLAIN 实证，详见证据文件）

- **索引生效路径**：general_log 抓取服务实发 SQL 原文 EXPLAIN ANALYZE——
  `Index lookup on a using idx_oa_process_user_create_time (user_id=3) (reverse) rows=10`，
  **0.113ms，无 Sort 节点**（回归态同形状 16.4ms，全量 10,001 行进排序堆）。
- **优化器不自发选索引**：单表形状会选（cost=661 反向扫描），但带三个 left join 的实发形状里
  `uk_oa_process_idempotency_key` 的 ref 成本仅低 0.45，优化器不认反向扫描的排序收益
  （optimizer trace：新索引 `cost=661.45 chosen=false`；ANALYZE TABLE 刷新统计后依旧；
  显式 `(user_id, create_time DESC, id DESC)` 降序索引同被拒）→ 改为按形状注入 hint。
- **配置实例查询（无 user_id）**：用不上该索引，hint 被忽略、计划不变——按 #185 Q1 决策
  接受全表排序（离 500ms 判定线余量大）。

## 4. 环境膨胀的定性（晚锚）

修复轮除 findStarted 外所有动作相对夜锚一致 +15~30%、吞吐 −11%——包括与 `oa_process`
完全无关的 login（sys_user+Redis）与 processTypeAll（配置小表），是均匀膨胀的环境签名
（#182 锚点凌晨 4:30 跑，本轮晚间跑）。**晚锚**（358dbbd 无修复代码，同快照同脚本同时段，
baseline 一档，吞吐 474.2、fail 0.004%、阈值全过）逐点验证：

- **回归在同时段原样复现**：晚锚 findStarted p95 157ms ≈ 夜锚回归态 154ms——环境膨胀
  解释不了回归，回归真实存在，且修复轮在同条件下的 −81.5%（29 vs 157）是纯修复收益。
- **膨胀与代码无关**：晚锚其余动作与修复轮逐点重合（login 250≈245、findPending 39≈37、
  findProcessed 169≈157、show 58≈53、processTypeAll 21≈19、approve 59≈56、startUp 91≈78），
  即同一晚间环境在无修复代码上同样膨胀 +15~30%。
- **写路径无回退**：修复轮对晚锚逐动作全部持平或更好（−2% ~ −14%），吞吐 +3.9%
  （492.5 vs 474.2）——V108 二级索引的插入维护成本在 20 VU 混合负载下不可见。

## 5. 与协议的偏差（均记录在案）

1. **时段不同**：#182 锚点为凌晨，本轮为晚间。跨时段数字只作参考不进判定；
   回退 ≤10% 的判定在晚锚同条件下评估。
2. **晚锚仅 baseline 一档**：为环境膨胀定性而设（膨胀幅度 +15~30% 远超轮间噪声 ±5%，
   单轮足以定性）；findStarted 的 −81% 亦远超噪声。
3. **#182 取证保真度订正**：`explain-findStarted-orderby.txt` 的 SQL 为手拼，比 mapper
   实发形状多带 `is_deleted = 0` 条件（实发 SQL 不过滤逻辑删除——手写 XML 不吃
   `@TableLogic`，已立 [#198](https://github.com/lautung/guigu-oa/issues/198)）。
   排序成本结论不受影响（两形态均为全量 10,001 行进排序堆）。本轮取证改用 general_log
   抓取的实发 SQL 原文。
4. **慢日志**：基线三轮零慢查询；stress-1 一条 0.13s group-commit 等待
   （Rows_examined=0，与 #124/#182「零业务慢 SQL」口径一致）。

## 6. 结论

- **#185 修复有效**：findStarted 基线 p95 154→29ms（晚锚同条件 157→29，−81.5%），mid/stress 同向
  （−66%/−58%）；SQL 层 16.4ms→0.113ms（反向索引扫描，LIMIT 短路）；八档阈值判定零失败；
  写路径（startUp/approve）对晚锚持平或更好、吞吐 +3.9%，V108 索引维护成本不可见。
- **instanceQuery 保持全表排序**（Q1 决策），p95 94ms 离 500ms 判定线余量大。
