# 业务单据与审批分属两态，回写单向

人事、考勤、报销三个域的单据都要经过审批。省事的写法有两种：把单据状态直接当成审批状态（列表、统计都读审批表），或者审批通过后才创建单据。前者让撤回、重新发起、草稿与附件无处安放；后者让业务统计依赖审批表，且草稿态没有单据行可挂。

决定：

- 每个域有自己的单据表与状态机（草稿/审批中/通过/拒绝/撤回等，具体档位由各域票定）；审批实例只作过程真相，两者由 business key 关联（形状由 #272 定）。
- 回写**单向**：审批结果（通过/拒绝/撤回）→ 单据状态；单据不反写审批。
- 发起与回写都在同一事务边界内，失败沿用 ADR 0012 的持久化副本 + 回滚补偿；幂等键形状由 #272 定。
- 业务单据用自己的 DTO 与 jsr303 校验（ADR 0033）；不把 form-create 表单值当单据数据。
- 单据在提交时快照部门、申请人与金额类字段；列表与统计读快照，不随调岗或组织调整漂移。
- 通用「发起审批」保留给无专用单据的模板；业务单据走域内发起页（蓝图 2.0 §2）。

考虑过的替代方案：

- **单据状态 = 审批状态**：撤回后单据回到哪个业务态、重新发起如何区分、审批结束后的台账统计都要跨表翻译审批状态；审批模型一变单据全跟着变。
- **审批通过后才创建单据**：草稿、票据附件、金额修改无处安放，「申请中」的单据在业务列表里不可见。
- **一张通用 JSON 单据表**：明细、票据、金额是结构化查询对象，JSON 丢类型、丢索引、丢校验。

后果：

- `oa_attachment` 需能挂业务单据（ADR 0002 修订）；业务域后台列表接数据范围（ADR 0053/0057 修订）。
- 每个域的实现票必须给出自己的状态机与回写点，不允许借用审批状态；「审批通过后单据怎么变」成为每域合同的固定用例。

Related: ADR 0002/0053/0057（需修订）；ADR 0004/0008（客户端待确认与失败证据语义沿用）；ADR 0012（回写补偿的形状）；issue #267/#268/#272。
