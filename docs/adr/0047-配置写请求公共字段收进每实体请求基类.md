# 配置写请求公共字段与落库填充收进每实体请求基类

#176（第三轮架构审查候选）：五对 Save/Update 请求 DTO 字段逐字同名、`@Size`/`@Min`/`@Max` 逐字相同，约束语义没有 locality——ADR 0036 的 `@Size` 约束波要五对 DTO 挨个成对改，纯靠细心保证两半不漂移。决定每实体收一个抽象请求基类，持有两半注解完全一致的字段与 `fill()` 落库填充；HTTP 契约一字不改（ADR 0034 的 seam、ADR 0036 的约束面、ADR 0035 的失败顺序契约原样）。

决定：

- 基类只收**两半注解完全一致**的字段（`@Size`/`@Min`/`@Max`/无注解 + 公共 `@Schema`）与 `protected void fill(entity)`；壳的 `toEntity()` 只剩自己的字段加 `fill()` 一行（update 先 `setId`）。上收：SysUser 2/5 字段（phone/status）、SysRole 1/3（description）、SysMenu 5/9（component/perms/icon/sortValue/status）、ProcessType 1/2、ProcessTemplate 6/8——长度约束此后改一处、两半同步。
- 必填性注解（`@NotBlank`/`@NotNull`）不上收，留在各壳：它不是复制，是 ADR 0034 seam 的两半语义（save 必填 / update 空=不覆盖）。基类出现必填性注解即视为破坏 seam。
- `password` 不上收：两半语义分歧（save 必填建号 / update 空即不改密），`@Schema` 描述本就不同。
- `sys_menu` 的 `@AssertTrue isPageComponentFilled()` 不上收：两半逻辑互补（save 判「type=1 时必填」，update 判「显式送空白必拒、null 放行」）——#176 里「逐行相同」的主张经核验不成立。方法名两壳一致，属性名 `pageComponentFilled` 参与全局排序的位置不变（ADR 0036 后果条）。

## 考虑过的替代方案

- **全上收 + 校验组（`groups = OnCreate`）**：字段全部进基类、必填性打组、save 控制器改 `@Validated(OnCreate.class)`。被拒：跨组违例顺序可能重排（如 `type` 越界 + `name` 缺失，单池按属性名排序是 `name` 在前，分组后 Default 组先跑会变成 `type` 在前），ADR 0035 的顺序契约会承实证型风险；springdoc 对分组注解的 OpenAPI 呈现不确定；五个控制器签名全改。收益只多出「必填性也单点」，而必填性本就该随缝分半。
- **只收 `toEntity()` 不继承**：deletion test 不满足——`@Size` 仍在两半漂移，约束波摩擦原样。
- **壳里重声明字段（遮蔽）复用基类**：基类字段与壳字段是两个成员，Bean Validation 双重校验，现在靠 `@Size` 对 null 放行才侥幸不炸，不可依赖。

## 后果

- 校验顺序不变：失败消息按属性名全局排序（`GlobalExceptionHandler` 拼接，ADR 0036），属性名一个未改；`RequestValidationContractTest` 34 条全量实证。
- springdoc 沿继承把基类字段展开进壳的 schema，OpenAPI 文档不变。
- 新写法约定：某字段两半约束一致→进基类；只一半有的约束→进壳；壳里引用基类字段走 getter（字段 private）。
- 回归锚点：`RequestValidationContractTest`（文案与顺序契约全量）、`FlywayMigrationContractTest`（良构体触发矩阵）、接口套件 `tests/api/b-menu.spec.ts`（B22 顺序契约，与合同测试 `configurationValidationRunsBeforeTheGrantGate` 同构）。
