# 权限模型收成页面、按钮点与数据范围三层

原模型把「配置权限」定义成「至少一项配置类页面」，页面级授予覆盖全部读写，并明确不引入按钮/动作权限（ADR 0013）。泛后台要长出用户、角色、菜单、部门、岗位、字典、参数、公告、日志、监控、工具十几组页面，页面级粒度不够：日志的删除/清空、用户的重置密码、在线用户的强退都需要按动作区分；若依的授权树本来也把按钮点挂在页面下，页面授予与按钮点是一棵树。

决定：

- 权限分三层：**页面授予、按钮点、数据范围**。三层都只作用于后台；办事组内置、登录即有，不参与授权；审批可见性仍由成员资格（申请人/当前处理人/历史处理人/抄送人）决定，不套数据范围。
- 菜单表继续用 `sys_menu` 一张表：`type` 0 目录 / 1 页面 / 2 按钮；按钮行带 `perms` 与 `parent_id`，挂在页面上。授权树、授予闭包、`/info` 都从这一张表出。不新建 `sys_permission` 表。
- **后台权限成立 = 至少被授予一个 `type=1` 页面**。只授目录不算；只授按钮不算；按钮点只随页面出现，不能单独构成后台权限。隐藏页（模板设置、分配角色）跟可见父级同一条授予。
- 多角色并集；用户没有直接授权。按钮点的前端语义是「无权限移除 DOM」（与若依 `v-hasPermi` 一致），后端是方法级 gate；按钮点不是菜单入口。
- 判定顺序不变：认证（401 + 208/209）→ 静态形状校验（200 + 201）→ 页面授予（200 + 205）→ 按钮点（200 + 205）→ service。校验先于授权沿用 ADR 0034；拒绝形状仍是 HTTP 200 + code 205。
- **管理员不硬编码**：没有 `user_id == 1` 或 `role_key == 'admin'` 旁路。种子 Flyway 建 `super_admin` 角色，授予全部页面/按钮点、`data_scope = 1`（全部），再赋给种子账号；新增菜单必须显式授予角色，管理员才看得见。
- `/info` 返回 `{ roles, permissions, menus }`：`menus` 为被授予页面及其祖先（含 `type` 与绝对路径），`permissions` 为按钮点标识集合；客户端据此注册路由、渲染授权树、执行 `v-hasPermi`。

考虑过的替代方案：

- **只做页面级**（否决）：日志清空、用户重置密码、在线用户强退这类破坏性动作无法按角色区分；用户最终选了全量若依式。
- **独立 `sys_permission` 表**（否决）：授权树、闭包、`/info` 要拼两张表，授予的父子关系还要再表达一次。
- **硬编码超级管理员**（否决）：ADR 0013 已把种子例外拿掉；旁路让授权 bug 在管理员身上永远看不见，也让数据范围的「全部」档失去意义。
- **前端只 disable 不删 DOM**（否决）：与若依范式不一致，且被禁用的按钮仍然暴露动作存在。
- **给按钮点再配一套缓存**（否决）：快照每次全量读小表，先不引入第二套失效路径。

后果：

- ADR 0013 的「不引入按钮/动作权限」被取代；种子角色从 `config_admin` 扩为 `super_admin`，由新迁移扩展，不重写历史。
- ADR 0036 的 `sys_menu.type` 值域 `{0,1}` 扩成 `{0,1,2}`；按钮点必须带 `perms`；长度约束不变。
- ADR 0007/0014 的分类与闭包形状调整：配置类 → 后台类，闭包输出页面授予 + 按钮点；授予权威仍是菜单树。
- 现有 35 个 gate 注解保留 path 语义，补按钮点；controller 不重写。
- 合同测试要覆盖：只授目录、只授按钮、叶子页面单独授予、按钮点缺失时 205、校验先于 gate、`/info` 形状。

Related: ADR 0007/0013/0014/0034/0036；issue #206/#208。
