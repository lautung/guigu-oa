# 来源地址只信任配置的受信代理

#262。登录失败计数、注册限流与操作日志的来源 IP 由客户端可写的 `X-Real-IP` / `X-Forwarded-For` 直接决定。Compose 又把后端 8800 直接映射到宿主：绕过 nginx 直连时，客户端可以轮换这两个头，让每次请求都落进新的限流桶；操作日志也会记录伪造来源。生产入口虽由 nginx 覆盖 `X-Real-IP` 并追加 `X-Forwarded-For`，但解析器不区分「请求是不是来自受信代理」，等于把代理链的信任关系交给了请求头本身。

旧实现对这两个头的处理还有两处隐含假设：先看 `X-Real-IP`、再取 `X-Forwarded-For` 最后一跳；地址字面量只做字符集/长度校验。前者让任意直连者都能自报来源，后者让 `999.1.1.1` 这类输入通过——本机 TUN DNS 会把它解析成真实地址，校验本身反而变成一次 DNS 查询。

决定：

- **一个端口、一个实现**：security 新增 `address/ClientAddressResolver`（`resolve(HttpServletRequest)`）与 `address/TrustedProxyClientAddressResolver`。登录过滤器、注册控制器、操作日志切面都注入同一个 bean，不再有静态 `of(request)` 读头。
- **默认不信任任何头**：`lautung.oa.security.trusted-proxies` 为空（默认）时只信 socket 对端。只有直接对端落在配置的 CIDR 内才进入转发头解析。
- **右侧优先的转发链**：对端受信时解析 `X-Forwarded-For`，从右向左跳过受信代理地址，返回第一个非受信跳；链为空/全是受信地址时再看 `X-Real-IP`，最后回落 socket 对端。nginx 追加的真实对端永远压过客户端预置的假跳。
- **纯语法地址校验**：IPv4 逐段 0–255；IPv6 按 `::`/分组数/内嵌 IPv4 做语法校验，不调用 `InetAddress.getByName`，请求头里的值不会触发 DNS。空白、超长（>45）、非 IP、坏跳都跳过，不制造假来源；取不到对端仍是 `unknown`。
- **配置错误不阻断启动**：非法 CIDR、重复、混族都接受解析；非法项 WARN 一次后剔除，按空列表处理。
- **Compose 只信 client 容器的固定地址**：固定子网 `172.31.250.0/24`（`DEMO_SUBNET` 可覆盖），client 静态地址 `172.31.250.10`（`DEMO_CLIENT_IP` 可覆盖），后端 `TRUSTED_PROXIES=172.31.250.10/32`。宿主直连 8800 的下一跳是网桥网关，虽然与 client 同子网但不在 `/32` 里，伪造头无效。
- **配置入口统一**：base `application.yml` 把 `lautung.oa.security.trusted-proxies` 绑到 `${TRUSTED_PROXIES:}`；生产部署由运维显式配置入口代理网段，本地默认空。
- **测试口径**：resolver 单测覆盖默认忽略、单/多跳、假跳、全受信链、带端口/IPv6、坏跳、大小写头名、非法 CIDR、空对端；合同测试 profile 信任 `127.0.0.1/32`（MockMvc 对端），另有一个显式覆盖为空 + 混入非法 CIDR 的合同测试证明默认忽略与启动容错；操作日志合同断言 `oper_ip` 是解析结果；安全套件改为「直连换伪造头仍进同一个注册桶」+「经 nginx 的登录审计记真实来源」。

考虑过的替代方案：

- **信任整个 Compose 子网**（否决）：Docker 的宿主直连对端是网桥网关（`x.x.x.1`），它就在子网里，信任整个子网等于重新打开直连伪造面。固定 `/32` 才同时满足「经 nginx 可区分」与「宿主直连无效」。
- **用 Spring 的 `server.forward-headers-strategy`**（否决）：该策略按容器/框架隐式生效，信任面不由配置显式表达；本票要的是一条可审计的信任边界。
- **保留静态 `ClientAddress` 只加配置分支**（否决）：调用方仍会各写一套规则，新增匿名端点容易绕开。
- **宽松接受任意非空头值作为来源**（否决）：伪造值与异常值会直接进限流键与审计行，长度上限也失去意义。
- **按账号等级/设备指纹做限流**（否决）：超出本票范围，且匿名面没有可信的账号维度。

后果：

- 未配置 `TRUSTED_PROXIES` 的部署里，登录/注册/操作日志的来源一律是 socket 对端；反向代理后的部署必须显式配置入口网段，否则所有用户共享代理对端这一个来源桶（限流更严、审计更粗）。
- `application-test.yml` 信任 `127.0.0.1/32`，既有用 `X-Forwarded-For` 区分来源的合同测试保持原语义；`ClientAddressTrustContractTest` 用空/非法配置另起上下文，证明默认忽略与非法 CIDR 不阻断启动。
- 安全套件的注册限流用例不再用注入 `X-Real-IP` 制造独立来源；改为轮换伪造头证明「不产生新桶」，以及经 nginx 的登录审计行证明真实来源不变。
- Compose 固定子网与静态地址带来一个本地约束：同一台机器并行跑多个 Compose 项目时可能撞网段，用 `DEMO_SUBNET` / `DEMO_CLIENT_IP` 成对覆盖。
- 地址解析不再有 DNS 副作用；`unknown` 兜底与 45 字符上限保留，计数键形状不变。
