# 报销单收成单头、明细与独立发票，审批快照复制附件

蓝图 2.0 把报销定为 W4，只钉了「单头 + 明细、票据附件、提交即发起、三态回写、台账与统计」与「不做发票号去重、Excel 导出、预算/借款/对公付款/税务」，票据字段与域内字段集留给本票（§9）。研究 #270 的事实是：四套实现都不用整数分；本仓 `oa_attachment` 只有 `process_id`/`draft_id`/`owner_user_id`，没有业务归属列，草稿 `PENDING` 附件 24 小时会被清理；`oa_process.business_type` 与 `oa_business_template` 仍是 ADR 0067 的未执行草案。ADR 0066/0067 已定两态、业务键、提交即发起、同事务回写与三分类终态；ADR 0071 已定业务单据「单号即 id」、状态档 0/1/2/-1/-2、数据范围列与详情读同套范围。本 ADR 定报销域的字段、发票与附件形状、回写点、台账与付款登记；不写实现。

## 决定

### 单据模型

- 三张表：`expense_claim`（单头）、`expense_claim_item`（费用明细，独立行表）、`expense_invoice`（发票元数据）。不做 JSON 明细数组，也不做通用 JSON 单据表。
- 单头字段：申请人 `applicant_id`（`sys_user.id`）、提交时部门快照 `dept_id`、事由 `reason`、合计 `total_amount`、状态、最近提交/终态时间、付款状态与付款人/时间。
- 明细字段：发生日期、费用类型、金额、说明、可选 `invoice_id`、排序。每条明细金额 > 0、日期不晚于今天、说明可空 ≤255；一单至少 1 条、最多 50 条才能提交。
- 合计由服务端按明细重算，不信任客户端；金额用 `DECIMAL(14,2)` 元 + `BigDecimal`，单币种人民币，不建币种列，也不做整数分。明细金额之和是台账与统计的唯一金额真相。
- 状态沿用 ADR 0071 的档位：0 草稿 / 1 审批中 / 2 通过 / -1 拒绝 / -2 撤回；文案是报销域自己的，不借审批状态（ADR 0066）。
- 费用类型走现有字典 `expense_type`（种子：交通/餐饮/住宿/办公/通讯/其他），运行时可维护；不建费用类型表。明细存字典值，提交时校验是启用字典值，展示走字典翻译。
- 单号即单据 id，不另设业务编号（与 ADR 0071 一致）。
- 申请人必须有所属部门：`dept_id` 是数据范围列，不允许空；无部门账号建单/提交按 201 拒绝。

### 发票与附件

- `expense_invoice` 一行一张票：归属 `claim_id`，发票号/代码/金额/开票日期全部可空，另有备注与排序。发票号**不唯一、不去重**（蓝图已裁决）。
- 基数：明细带可空 `invoice_id`；一张发票可被多条明细引用，一条明细最多一张发票；需要多张票的明细拆成多行。明细引用的发票必须属于同一张报销单（服务端校验）。
- 发票可选：明细可以没有发票；不做「发票金额合计 = 报销合计」硬校验，只在页面上显示差额，避免小额零星支出无法报销。发票行至少要有文件或发票号之一，避免空行。
- `oa_attachment` 增加 `business_type VARCHAR(64)` / `business_id BIGINT`（镜像 `oa_process` 的业务键），文件归属业务行：发票文件 `business_type='expense.invoice'`、`business_id=expense_invoice.id`。不新建文件表，元数据表仍是权威（ADR 0002 修订）。
- 业务归属附件确认后复制为永久对象并直接 `ATTACHED`，不进入草稿 `PENDING` 的 24 小时清理；`owner_user_id` 仍是上传人。上传入口在现有 `/admin/attachments` 上增加业务键分支，文件类型与大小限制沿用现有附件规则。
- 提交时把当前发票文件复制成审批快照：新 `oa_attachment` 行、`process_id` 指向新审批、业务键留空；对象也复制为 process 拥有的永久对象（新 `storage_id` 与永久 key），不与业务附件共享 `object_key`。审批详情与审批成员下载走 ADR 0011；业务侧行保持业务归属，审批中不再改。
- 附件上传/下载的业务侧 gate 经 process 模块的只读端口由业务域回答（上传 = 本人且单据可编辑、发票属于本单；下载 = 本人或数据范围可见），process 不依赖 expense，沿用 ADR 0011 的端口形状；审批快照附件仍走成员资格。
- 发起端口需支持把当前发票附件 ids 带入快照，由 process 在引擎启动前完成对象复制与 `process_id` 绑定（与现有 `bindDraft` 同位置），业务域不直接写 `oa_attachment.process_id`；这样不新增「引擎已启动而快照未复制」的缝隙。
- 附件对象不按行删除：只有没有任何未删附件行引用该 `object_key` 时才物理删；提交后不物理删，终态保留。草稿删单连带软删单据/明细/发票/附件元数据；草稿删除发票时引用它的明细 `invoice_id` 置空。
- 发票与业务附件在审批中冻结；拒绝/撤回后可编辑，重提时按当时的文件集重新复制快照，旧审批的副本不动。审批侧的补传仍按 ADR 0011，不改变单据与业务附件。

### 审批关系

- `business_type` 常量 `expense.claim`（ADR 0067 的值域 `<域>.<单据>`）。
- 提交 = 草稿/拒绝/撤回 → 审批中的状态 CAS + 校验 + 合计重算 + `BusinessApprovalStarter`（客户端幂等键必填）+ 附件快照复制，同一事务；模板按 `oa_business_template('expense.claim')` 解析，缺失/未发布/发布证据失效 → 发起 201 拒绝、单据留草稿。
- 回调三分类：`APPROVED` → 2 通过、`REJECTED` → -1 拒绝、`WITHDRAWN` → -2 撤回，并写终态时间；同值幂等 no-op、不同值抛错回滚（ADR 0067）。
- 通过后锁定，不再接受修改或重提；要改另立新单。拒绝/撤回保留在「我的报销单」，可改后重提同一单据，单号不变；重提时 `dept_id` 按当前部门重新快照，在途审批各自冻结。
- 审批详情的提交快照：摘要（单号、申请人、部门、事由、合计、明细条数）+ 明细逐条文本 + 发票文件。审批人不开业务后台页（ADR 0067），审批成员下载快照附件（ADR 0011）。
- 「我的报销单」详情显示最近一次审批摘要与同一业务键的审批历史（只读链接）；审批详情本身仍按成员资格 gate 打开。

### 台账与统计

- 后台台账只读**已提交过**的报销单（审批中/通过/拒绝/撤回），草稿只在本人办事面；默认按提交时间倒序，默认状态为已通过，可筛选审批中/拒绝/撤回/全部（永不出现草稿）。筛选维度：状态、费用类型、明细日期区间、申请人、部门、付款状态。
- 付款登记：`pay_status` 0 未付 / 1 已付 + `paid_time`/`paid_by`；只有已通过的报销单可登记；`expense:claim:pay` 一个按钮点。允许同权限撤销（已付 → 未付，清空付款字段），写操作日志；不改审批状态机，不做付款凭证、银行流水或会计凭证。
- 统计按 `expense_claim_item.expense_date` 归月，维度为月份 × 费用类型，指标为金额与笔数；只算已通过（付款与否不影响统计）；本人/部门/公司范围由数据范围切。另给本月/本年/待付款三个合计卡。
- 不建台账表或统计表，全部派生查询；不做 Excel 导出（蓝图）。

### 权限与页面

- 后台：一级目录 `/business`、二级目录 `/business/expense`；两页 `/business/expense/ledger`（报销台账）与 `/business/expense/stat`（统计）；页面授予按路径走 `@backofficeGate.isAllowed(路径)`，付款按钮点 `expense:claim:pay`；读端点只判页面授予。
- 办事：`/work/my-expense`（我的报销单，列表/详情/编辑/新建），登录即有、不套后台授权与数据范围，构造上只读本人。
- 数据范围：台账/统计/后台详情/业务附件下载都按 `dept_id` + `applicant_id` 套五档（ADR 0053/0057），详情与附件不能靠 ID 绕过列表范围；办事面只读本人。
- 审批人看审批详情快照与 process 附件，不给业务后台页权限；财务是角色 + 页面授予，不是新数据范围档（蓝图）。
- 种子一个 `finance` 角色：报销台账/统计两页 + `expense:claim:pay`，数据范围全部；种子数据可改，不写死在代码。
- 菜单/字典/角色/业务模板映射种子随迁移建，`super_admin` 补授保持幂等；首版不为 `oa_business_template` 开管理页，映射由迁移种子与部署维护。
- 服务端接口沿用 `/admin/...` 前缀、`Result` 信封与 `/{page}/{limit}` 分页；业务接口前缀 `/admin/expense/...`，个人面 `/admin/expense/my/...`，不新造 `/business` API 前缀。

### 首版不做

预算、借款、对公付款、税务、发票号去重、Excel 导出、多币种、OCR 与发票查验、付款网关与会计凭证、费用标准与超标校验、审批人核定金额与逐项审批（审批只对整单通过/拒绝）、纸质单据签收、收款账户与报销方式字段（付款线下完成）。

## 表结构草案（不执行）

沿用仓库约定：无外键；公共字段 `create_time`/`update_time`/`is_deleted`；索引单独 `CREATE INDEX`（MySQL/H2 双兼容）。

```sql
CREATE TABLE expense_claim (
  id BIGINT NOT NULL AUTO_INCREMENT,
  applicant_id BIGINT NOT NULL,              -- sys_user.id
  dept_id BIGINT NOT NULL,                   -- 提交时部门快照；重提更新
  reason VARCHAR(255) DEFAULT NULL,          -- 提交时必填
  total_amount DECIMAL(14,2) NOT NULL DEFAULT 0.00,  -- 明细合计，服务端重算
  status TINYINT NOT NULL DEFAULT 0,         -- 0 草稿 / 1 审批中 / 2 通过 / -1 拒绝 / -2 撤回
  submit_time DATETIME DEFAULT NULL,         -- 最近一次提交
  finish_time DATETIME DEFAULT NULL,         -- 最近一次终态（通过/拒绝/撤回）
  pay_status TINYINT NOT NULL DEFAULT 0,     -- 0 未付 / 1 已付
  paid_time DATETIME DEFAULT NULL,
  paid_by BIGINT DEFAULT NULL,               -- sys_user.id
  create_time DATETIME DEFAULT NULL,
  update_time DATETIME DEFAULT NULL,
  is_deleted TINYINT NOT NULL DEFAULT 0,
  PRIMARY KEY (id)
);
CREATE INDEX idx_expense_claim_applicant_status ON expense_claim (applicant_id, status);
CREATE INDEX idx_expense_claim_dept_status ON expense_claim (dept_id, status);
CREATE INDEX idx_expense_claim_status_submit ON expense_claim (status, submit_time);

CREATE TABLE expense_claim_item (
  id BIGINT NOT NULL AUTO_INCREMENT,
  claim_id BIGINT NOT NULL,
  expense_date DATE NOT NULL,
  expense_type VARCHAR(64) NOT NULL,         -- 字典 expense_type
  amount DECIMAL(14,2) NOT NULL,
  description VARCHAR(255) DEFAULT NULL,
  invoice_id BIGINT DEFAULT NULL,            -- expense_invoice.id，同单校验
  sort_no INT NOT NULL DEFAULT 0,
  create_time DATETIME DEFAULT NULL,
  update_time DATETIME DEFAULT NULL,
  is_deleted TINYINT NOT NULL DEFAULT 0,
  PRIMARY KEY (id)
);
CREATE INDEX idx_expense_item_claim ON expense_claim_item (claim_id);
CREATE INDEX idx_expense_item_invoice ON expense_claim_item (invoice_id);
CREATE INDEX idx_expense_item_type_date ON expense_claim_item (expense_type, expense_date);

CREATE TABLE expense_invoice (
  id BIGINT NOT NULL AUTO_INCREMENT,
  claim_id BIGINT NOT NULL,
  invoice_no VARCHAR(64) DEFAULT NULL,       -- 不唯一、不去重
  invoice_code VARCHAR(64) DEFAULT NULL,
  amount DECIMAL(14,2) DEFAULT NULL,
  invoice_date DATE DEFAULT NULL,
  remark VARCHAR(255) DEFAULT NULL,
  sort_no INT NOT NULL DEFAULT 0,
  create_time DATETIME DEFAULT NULL,
  update_time DATETIME DEFAULT NULL,
  is_deleted TINYINT NOT NULL DEFAULT 0,
  PRIMARY KEY (id)
);
CREATE INDEX idx_expense_invoice_claim ON expense_invoice (claim_id);

ALTER TABLE oa_attachment ADD COLUMN business_type VARCHAR(64) DEFAULT NULL;
ALTER TABLE oa_attachment ADD COLUMN business_id BIGINT DEFAULT NULL;
CREATE INDEX idx_oa_attachment_business ON oa_attachment (business_type, business_id);
```

## 种子草案（不执行）

- `sys_menu`：目录 `/business`、目录 `/business/expense`、报销台账/统计两页与 `expense:claim:pay` 按钮点；办事入口「我的报销」；补授 `super_admin`，保持幂等。
- `sys_dict_type` / `sys_dict_data`：`expense_type`，演示种子给交通/餐饮/住宿/办公/通讯/其他。
- `sys_role`：`finance`（数据范围全部），授予报销台账/统计与付款按钮；不自动绑定任何账号，由管理员分配。
- `oa_business_template`：`expense.claim` 映射到一份已发布审批模板；映射由迁移建，模板本身由部署/演示种子准备。演示模板审批人用部门负责人（ADR 0065/0069 的动态审批人），单节点线性，不做金额条件分支。
- 迁移编号从下一可用版本起（截至本 ADR 为 V133，报销实现票取届时的下一可用号）；索引建完用实发计划验（#185 教训），H2 合同测试跑真迁移。

## 考虑过的替代方案

- **金额存整数分**：需要每处换算与展示约定，四套参考实现都没这么做；MySQL `DECIMAL` 是精确值，`BigDecimal` 与现有 Java 栈一致。
- **建币种/汇率列**：单币种下永远是常量；多币种本质是原币、公司币种与汇率的快照问题，不是加一列能解决。
- **明细用 JSON 数组（芋道形状）**：丢独立 id、外键、索引与生命周期，台账统计与发票关联都做不了。
- **不建发票表，只挂文件**：发票号/代码/金额/开票日期没有地方存，票据只能是一堆匿名文件。
- **明细 ↔ 发票 N:M 关联表**：首版只有「一张发票挂多条明细」的诉求；一条明细多张票用拆行表达，不值得多一张关联表。
- **审批快照共享附件行（同时带 process_id 与业务键）**：拒绝后改单重提会让上一次审批的历史详情跟着变，破坏提交时快照。
- **审批详情直接读业务附件**：审批人需要业务后台页权限，违反 ADR 0067。
- **物化台账表/统计表**：数据量是小团队，派生查询足够；多一张表就多一处与单据状态的同步真相。
- **付款状态并进单据状态档（如加「已付款」）**：审批状态机只有三分类终态，付款是财务动作，混进去会让回写与统计都跨状态翻译。
- **不做付款登记（只到审批通过）**：小团队真跑时申请人不知道钱到没到，财务也没有可核对的已付清单。
- **审批人核定金额/逐项通过**：首版审批只对整单通过/拒绝；需要改金额就拒绝后重提。
- **发票号唯一索引/重复检测**：蓝图已明确首版不做；跨单据重复检测是另一个产品问题。
- **后台台账包含草稿**：草稿是未完成品，属于本人办事面；财务口径从提交开始。
- **提交后允许删单**：审批行按业务键指向单据，删单会让历史审批断链；只允许删草稿。

## 后果

- ADR 0002 需修订：附件可挂业务单据，元数据表仍是权威；业务附件不进草稿 TTL 清理，下载 gate 从成员资格扩到业务单据读权限。
- ADR 0053/0057 的数据范围接入点扩到报销台账、统计、后台详情与业务附件下载；五档语义、并集、空集与不缓存不变。
- 新增 `lautung-oa-expense` 模块：依赖 `process`（业务审批端口 + 附件业务键端口）、`security`（`DataScopeProvider`）、`dict`（`expense_type` 校验）、`model`、`framework`、`common`；不依赖 auth（用户/部门展示走 SQL join）；ArchUnit 层规则扩到 expense → process/security/dict 与 server → expense，process/auth/dict 不反向依赖 expense。
- 附件服务当前没有「删除/解绑已 `ATTACHED` 附件」的公开方法，只有 pending 删除与对象级删除；业务键分支要新增端口与 service 方法，草稿删文件走业务分支，提交后不删。
- 实现顺序：先落 ADR 0067 的业务键列、发起/回调端口与 `oa_business_template`（W1），再落报销域；否则报销提交没有可用的发起端口与模板映射。
- 实现票必须给出：状态机与回调、`expense.claim` 常量、模板映射与演示模板、菜单/字典/角色种子、三页与办事面、API 形状、`oa_attachment` 业务键改造、附件快照复制与对象引用删除、数据范围五档合同测试、H2 真迁移。
- 蓝图 §9 的「票据字段」由本 ADR 收口；W4 实现票可直接按本 ADR 拆。
- GLOSSARY 增补报销单、费用明细、发票、报销台账、付款登记。
- 未决：`oa_business_template` 的管理入口（首版不开，改映射走种子/部署）；P1 两域与报销无耦合。
