# 审批写入收成一个实现，引擎收成端口，附件回滚只删新副本

审查候选 6 把 `startUp/approve` 的次序、Flowable 命令和附件绑定放在同一个 `void` service 里：`interface` 不表达「账本先写、附件绑定后、引擎再启动」，并发合同测试只能反射替换私有 `taskService`，对象存储的 permanent copy 在事务回滚后也没有测试面。现在把两个写入动作搬进 `process.approval.ApprovalWriter`，由它独占 `@Transactional` 和次序；`Approval` 仍是公开 interface，`OaProcessServiceImpl` 只保留读并委托写入。写入成功返回 `Approval.StartOutcome(processId, processInstanceId, currentTaskIds)` / `DecisionOutcome(processId, status, nextTaskIds)`；失败仍抛现有 `GuiguException`，HTTP 仍是 `Result.ok()`，客户端 `ApiResponse<void>` 和 ADR 0004/0008 的「待确认」都不变——服务端返回类型不能表达客户端没收到响应，超时不确定性仍由客户端分类。

Flowable 命令收成 `ApprovalEngine` 端口：`start`、`complete`、`rejectToEnd`、`currentTasks`，返回 `CurrentTask(taskId, assignee)`，不泄露 Flowable 类型；`FlowableApprovalEngine` 委托 `ProcessEngineApproval`，后者仍是唯一 Flowable 调用点。账本、附件、抄送、审批人姓名不另造 port：`ApprovalWriter` 直接用 `OaProcessMapper`、`OaProcessRecordService`、`AttachmentService`、`CarbonCopyWriter`、`SysUserService`，并由真实 DB 合同测试证明事务。次序保持现状：账本 insert → 抄送 → 附件绑定 → 引擎 start → 账本 update → 流转记录；approve 是引擎 complete/reject → 流转记录 → 读下一任务 → 账本 update。引擎 start 需要 `oa_process.id` 作 businessKey，账本必须先写；附件在引擎前绑定，commit 时不会出现「流程已启动但附件对象还没到位」。

附件回滚补偿收进 `AttachmentService.bindDraft`：在每次 copy 之前注册 `afterCompletion(STATUS_ROLLED_BACK)`，回滚时 best-effort 删除本次新产生的 permanent copy；pending/temp 对象保留，附件行回到 PENDING 后仍可重试；删除失败只 WARN，现有 `cleanupExpiredPending` 在 TTL 后同时清两个 key，作为兜底。这样回滚不会让用户已上传的文件消失，也不会把未提交的 permanent copy 留在桶里。

代价：写入仍依赖 MyBatis 服务，不是纯模块，事务语义仍由真实 DB 合同测试证明；`Approval` 的方法签名变了但 wire contract 没变；outcome 的 task id 顺序不保证；没有 `ApprovalLedger` port，如果将来出现第二个账本 adapter 再补。测试面改为 `ApprovalContractTest` 的 `@Primary` 测试 adapter（engine barrier/failure hook）和共享 `TestAttachmentObjectStore`，合同测试不再反射私有字段；新增顺序、outcome、engine 失败、附件批量中途失败和回滚重试断言。

Related: ADR 0002（附件挂在审批实例、元数据表权威）；ADR 0004/0008（客户端待确认与失败证据）；ADR 0011（membership gate 不变）。
