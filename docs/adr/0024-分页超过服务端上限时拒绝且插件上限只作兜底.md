# 分页超过服务端上限时拒绝，插件上限只作兜底

#137 复现出一个 S3：`GET /admin/system/sysUser/1/100000` 与 `GET /admin/process/findPending/1/100000` 都返回 `code=200`，把整表记录一次带回；`PaginationInnerInterceptor` 没有设 `maxLimit`，负数与零也被当成普通页大小。公开的只读入口因此可以被低成本地用来放大内存与带宽。

现在一次 HTTP 分页读取的窗口由 `PageWindow` 拥有：页码必须 ≥ 1，每页必须在 1..500 之间，越界在查询前抛出 `GuiguException(201, ...)`，响应体仍是既有的 `Result` 形状（`code=201`、`data=null`），不进入 service。九个分页入口——用户、角色、审批类型、审批模板、审批实例五个配置页，待处理、已处理、已发起、抄送我的四个办事页——都通过 `PageWindow.of(page, limit)` 构造 `Page`，不再自己 `new Page<>(page, limit)`。

上限取 500：客户端 `ListPagination` 提供的页大小最大 100，演示造数与测试内部读取最大 100，500 留出余量但挡住整表拉取。选择**拒绝**而不是静默截断：截断仍会让一次请求取走 500 条，并以 200 掩盖调用方越界；拒绝让调用方知道这次读取没有按请求执行，也满足安全用例「超大 limit 不被接受」的判定。

`PaginationInnerInterceptor` 同时设 `maxLimit=500`，兜住直接走 MyBatis-Plus 的分页查询：不经过 HTTP 入口的调用方（现在只有演示造数与测试）也最多取 500 条。它只作用于 MyBatis-Plus 生成的 SQL；待处理、已处理走 Flowable 任务查询，抄送我的走原生 `LIMIT`，这三条路径的 500 上限只由 HTTP 边界的 `PageWindow` 保证。插件这一层是截断而不是报错，因为它不面向请求参数；HTTP 边界上的拒绝语义由 `PageWindow` 负责。

否决的替代方案：只设插件 `maxLimit`——响应仍为 200，越界被掩盖，安全用例不通过；只在 Controller 手写 `if`——九个入口重复同一段判断，边界一改就要改九处；用 Bean Validation 注解 + 400——会绕开现有 `Result` 包装与客户端 `code` 识别，客户端还要多认一种传输失败；按端点分别配上限——目前没有第二个上限的证据。

代价：任何真正需要 >500 条的内部调用会被插件截断；返回给客户端的是 `code=201` 与中文消息，客户端按业务失败展示。测试新增 `PageWindow` 单元用例与覆盖九个入口的 HTTP 合同（100000 复现、501 边界、0/-1 页码、500 与 1 的接受值）。
