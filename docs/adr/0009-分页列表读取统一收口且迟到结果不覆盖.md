# 分页列表读取统一收口，迟到结果不覆盖

分页列表的“当前这次读取”由前端一个 `createListRead` module 统一拥有，覆盖办事四种列表（待处理、已处理、已发起、抄送我的）与五个配置分页页（用户、角色、审批类型、审批实例、审批模板），共九种列表、六个组件；树形的菜单管理与菜单授权不在范围内。module 只拥有读取生命周期——已应用的页码、页大小与查询、加载与失败状态、最新一次读取生效（latest-wins）、重试与识别作用域；行的展示（标题、空态文案、字段映射）继续由各页现有的纯 presenter 完成；module 只保存原始记录，因此办事页与配置页的展示差异不会进入 module。页面只提供一个 `toRequest(command)`（多数就是现有的 `listRequest` 或 `workListRequest`），并渲染只读 view。

一次读取属于一次页面打开：module 在页面创建时建立并自动读取一次，离开页面或切换列表种类时 `release()`；切换种类建立新的 opening，不跨路由缓存，也不引入应用级 store。列表没有必须跨导航保留的待确认状态，待处理、已处理、已发起在每次处理后会变化，回到列表重新读取比缓存更符合现有语义。

最新一次读取生效由单调递增的读取序号与 `release()` 共同保证：只有最新一次读取可以提交结果，被取代的读取和已释放 opening 的续作都不再写入 view。不使用 AbortController：`ApiClient` 没有 signal，取消会以另一个失败经过 `request.ts`，需要额外区分且会让一次正常取代出现在错误通道里；接受少量浪费的网络工作，换取一条可测试的丢弃规则。opening 创建时捕获 recognition 上下文，请求携带 `_recognition` 与 `_isRelevant`，因此上一次进入身份的读取不能画到当前用户页面上。`invalid`、`disabled`、`superseded` 属于识别层已处理的终态，不进入列表的失败态；列表读取使用 `normalErrorNotification: 'caller'`，失败只由列表呈现一次，不再叠加全局提示。

失败与空态明确分开：只有 `ready` 且零记录才显示“暂无…”，失败显示可重试的错误；读取中与失败时保留上一次成功结果，由加载遮罩或错误条呈现，避免把“没读到”画成“没有数据”。module 保存已应用的读取命令，页面继续持有输入框里的草稿查询；`read({ page?, size?, query? })` 先应用再读，`read()` 重放上一次命令供失败重试与保存、删除后的刷新，页大小变化在没有显式页码时回到第一页。这样重试不会悄悄使用用户改了但未提交的输入。

旧的读取入口随 module 一并删除：`loadWorkList`、`findPage`、`afterPendingAction` 及其测试不再保留，`WorkListPage` 的标题与空态改用纯 `workListDefinition(kind)`；`workListRequest`、`presentWorkList` 与各配置模块的 `listRequest` / `presentListPage` 继续作为页面侧的纯适配器。module 的合同测试覆盖切换种类、翻页与搜索三种迟到读取、`release()` 中断在途、终态识别失败、失败后重试重放同一命令、页大小重置，以及空态与失败态的区分；不新增组件测试或浏览器用例，页面接线由类型检查与现有端到端覆盖。

否决的替代方案：只做“审批列表 opening”会让唯一调用方是一个已经复用四种列表种类的组件，leverage 名不副实，五种配置列表继续保留同一竞态；只做路由 key 加读取序号的局部修复能修办事列表，但把同样的失败与竞态留给配置列表；让 module 只收 `fetchPage` 会把识别作用域在六个页面各写一遍；使用 AbortController 在现有 `ApiClient` 上需要新增取消语义，收益不足以抵消复杂度。明确不做：删除最后一行后的页码回退、树形页面、后端协议变更、跨路由缓存与跨标签页协调。
