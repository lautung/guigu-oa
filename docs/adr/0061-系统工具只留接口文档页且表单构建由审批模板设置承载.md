# 系统工具只留接口文档页，表单构建由审批模板设置承载

#234 要把蓝图里系统工具组的 P1「接口文档」与 P2「表单构建」定到可实现形状。侦察到四件与票面假设不一致的事实：

- **表单构建已经存在**：审批「设置 → 模板设置」页就是 form-create 设计器（`client/guigu-oa-client/src/views/config/processTemplate/templateSet.vue:101`）加预览（`:105`），产出直接落 `oa_process_template.form_props/form_options`；新建模板的「类型/名称/保存未发布」由向导承担，服务端按 form-create 语义校验必填（ADR 0035）。蓝图 P2 那一行描述的是已有能力，不是待建页面。
- **客户端没有 iframe 或外链菜单机制**：路由 meta 只有 `title / menuGroup / hiddenParentPath / workListKind`，`sys_menu` 也没有 `is_frame`/external 列；全站唯一的「另开窗口」是模板列表的预览。
- **代理只覆盖 `/dev-api/`**：Vite（`client/guigu-oa-client/vite.config.js:15-20`）与 nginx（`client/guigu-oa-client/nginx.conf.template:26-27`）都把 `/dev-api/` 重写到服务端根；而 Swagger UI 内部取 spec 用的是绝对路径 `/v3/api-docs`，所以从 `/dev-api/swagger-ui.html` 打开会取不到 spec。
- **文档端点匿名且不区分 profile**：springdoc 3.1.0 仅 dev 开启（`application-dev.yml:67-73`），demo/prod 关闭；但 `/v3/api-docs/**`、`/swagger-ui/**` 在 `PublicApiPaths` 里是无条件 permitAll（`WebSecurityConfig.java:127-130`），「开放与否」实际只由 profile 开关决定。

决定：

- **表单构建不设独立页**：它由「审批设置 → 模板设置」承载，蓝图 P2 该行改为说明这一点。不做 designer 沙盒（产出没有落点，用户还得手动贴回模板设置），也不复制模板向导做「设计完直接存成未发布模板」的第二条路径。真出现「表单片段跨模板复用」的需求时另起票。
- **接口文档页 = 新窗口按钮 + 挂载探测**：页面挂载时探测 `/v3/api-docs`，200 显示主按钮「打开 Swagger UI」（`window.open('/swagger-ui.html')`）与端点路径说明；404、网络错误、超时一律归并为「当前环境未启用接口文档，仅开发环境提供」，不写启用方法——那属于开发文档，不属于产品面。不做第三种「探测失败」中间态。
- **同源代理补两段**：vite 与 nginx 各加 `/v3/` 与 `/swagger-ui` 的转发到服务端，页面里统一用绝对路径。springdoc 配置不动（`api-docs.path` / `swagger-ui.path` 保持默认）。
- **端点保护维持现状**：匿名白名单 + 仅 dev 启用，由 `OpenApiExposureConfigTest` 的 profile 矩阵钉住。把耦合写进本 ADR：**若未来在 demo/prod 重开 springdoc，必须同步把文档端点移出匿名白名单**——白名单不区分 profile，vite/nginx 的 `/v3`、`/swagger-ui` 两段也会立刻成为通路。页面本身在 `/tool` 下，靠页面授予进入，「打开文档」不设按钮点（只读页无写操作，与缓存监控、服务监控一致）。
- **代码生成不写说明**：蓝图 §9 已裁决「不进」，工具页只列可用工具，负向清单不进产品面。
- **菜单种子**：目录 `/tool`（type 0，`Layout`）+ 页面 `/tool/api-doc`（type 1，`tool/api-doc/index`，perms 空），只显式补授 `super_admin`，无按钮点；形状照 `monitor_online_menu_v117.sql`。

考虑过的替代方案：

- **iframe 内嵌 Swagger UI**（否决）：要新增 iframe 页机制（meta 约定、外链菜单、尺寸跟随），而 Swagger UI 的 inline script 还会撞 nginx 的 `script-src 'self'`；为一个能新窗口打开的页面不值得。
- **纯静态说明页**（否决）：dev 下可行，但 demo/prod 的「未启用」与 dev 的「可用」无法区分，页面会在两种环境里撒谎。
- **空态里写「如何启用」**（否决）：配置说明属于开发文档；产品面只回答「现在能不能用」。
- **独立沙盒页 / 独立页直接产出审批表单**（否决）：前者产出无落点，后者复制模板向导；两者都要多一套菜单、权限点与校验语义。
- **文档端点改 authenticated，或白名单按 profile 分支**（否决）：风险面已被「demo/prod 关闭 + 合同测试」收住，为一个开发便利面改安全链，复杂度高于收益；也会推翻 #140 已定的「dev 匿名可读」基线。

后果：

- nginx 的 `/v3`、`/swagger-ui` 两段在 demo/prod 是惰性的：springdoc 关闭时它们只把 404 透传回来；若在该环境重开文档，这两段会立刻成为匿名通路，与上面的白名单耦合是同一件事，必须一起处理。
- 蓝图三处（接口文档行、表单构建行、系统工具分组）随实现票更新，与菜单种子同一提交，避免「表单构建已由模板设置承载」与代码脱节。
- 系统工具模块本期只有一张页面；`/tool` 从 `ModulePlaceholder` 变成带子路由的目录，`shell-nav.ts` 的占位模块随之移除。
