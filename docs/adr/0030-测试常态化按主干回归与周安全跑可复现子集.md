# 测试常态化：PR 维持轻量，push main 跑栈回归，每周跑安全，性能留本地

生产加固（#107）结束后，五类测试只有手动入口；常态化要决定哪些套件、什么节奏、跑在哪里。
决定：**PR 门禁维持现状**（服务端测试 + 客户端 `verify` + Chromium 两档 mock e2e + 构建）；
**push 到 main** 后在 GitHub 托管 runner 起干净 Compose 栈，跑接口 66 条、功能 27 次运行、
兼容全矩阵 189 次运行；**每周一 03:00 UTC** 跑安全整轮（61 条定向 + ZAP 被动 + 存储型 XSS）；
性能全档位与完整证据链只在发布/演示/大修复后用本地 `scripts/test-round.sh all` 跑。
routine 运行 0 重试，红了先修再继续；证据作为 Actions artifact 保留 14 天，不入仓。
38 条从不编译/执行的 Activiti 7 测试及其 pom 排除一并删除。

理由：性能结论只在同机同快照下成立，共享 runner 的数字不可比；安全轮含 5 分钟上传凭证
TTL 等待，放周任务不拖慢合入路径；仓库是 private，Actions 按分钟计费，主干触发 + 周任务
把月用量控制在免费额度内；本地全轮仍是唯一能产出可信性能与完整证据的入口。

## 考虑过的替代方案

- **五类都进 PR 门禁**：反馈从 ~9 分钟涨到 15+ 分钟；PR 上跑共享 runner 的性能数字没有决策价值。
- **自托管 Mac runner**：省分钟数，但要求机器常开、与开发环境隔离，维护成本高于收益。
- **nightly 跑全部可复现套件**：push-main 已给出合入即时的信号，nightly 只多捕捉「没人 push 的静默漂移」。
- **自动开 issue 记录红**：没有第二个人接手时会变成噪音；GitHub 的失败通知足够。
- **routine 证据入仓**：会迅速超过 5MB 证据上限；routine 的价值是「这次红没红」，不是长期证据链。

## 后果

- push main 的 CI 从 ~9 分钟增加到 ~15 分钟（栈回归 job 约 6–8 分钟）；周安全 job 约 8–10 分钟。
- 当前是直接 push main，required status checks 拦不住直推；「红了先修」是纪律，不是强制门禁。
  要强制就改成 PR-only 工作流。
- 删除 38 条死测试后，服务端源码口径与执行口径一致（333），pom 里不再需要两条排除。
- 安全缺陷仍走「确认后开 `bug` + `severity:Sx` issue」的既有流程，routine 不自动建票。

## 补充（2026-11-04）

纯文档变更（`docs/**`、`**/*.md`）不再触发 CI 与栈回归；`ci.yml` 另加 `concurrency`
（同 ref 连推取消旧 run）。起因是实测两分钟内两个 markdown 提交各跑满一次 CI（12m19s、10m12s）
加一次栈回归（14m38s）。代价：只改文档的 PR 不产生 check，`check:docs` 的漂移由下一次代码变更
或本地 `verify.sh` 兜；ADR 编号与链接错误本地仍会在 `npm run verify` 里暴露。
