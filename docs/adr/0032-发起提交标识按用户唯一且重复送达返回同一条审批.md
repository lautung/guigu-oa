# 发起提交标识按用户唯一且重复送达返回同一条审批

`ApprovalWriter.startUp` 过去每调用一次就新建一条 `oa_process` 并起一个流程实例，服务端没有任何
去重键。双击已被客户端挡住（`sending` 阶段锁住所有变更，单测覆盖），但传输层重放——代理重发、
弱网重放、将来可能加的自动重试——仍会落成两条「要人处理」的审批，并同时通知审批人两次。

客户端本来就有正确的键：`SavedStart.id`（`approval-start.ts`）在一次发起尝试内稳定，恢复会话
后不变，`prepareStartAgain` 换新的。`draftId` 不能当键——重新发起时它被原样保留（附件继续复用
同一个草稿），拿它去重会把「重新发起」静默吞成同一条审批，和 GLOSSARY「重新发起可能另产生一条
审批」直接冲突。

决定：`ProcessFormVo` 增加可空 `idempotencyKey`（≤64 字符；空白或超长按 201 拒绝）；
`oa_process` 增加可空 `idempotency_key` 列与按用户唯一的索引
`uk_oa_process_idempotency_key (user_id, idempotency_key)`；同一用户同一标识的重复送达返回第一次
那条审批（响应形状不变，仍是空体 `Result.ok()`），不比对表单内容。没带标识的请求（旧客户端、
接口/栈/安全测试）照旧每次新建。索引按用户而不是全局：键只对「同一个人同一次提交」有含义，
全局唯一会让别人的请求撞上你的键后读到你的审批。

冲突兜底分两层：`startUp` 事务内先按 `(user_id, idempotency_key)` 预查（普通超时重试的最常见
路径，不抛异常），未命中才带键插入，由唯一索引裁决；命中唯一索引或其它 `DuplicateKeyException`
的调用方必须在事务之外——`OaProcessServiceImpl.startUp` 没有事务——再调用
`ApprovalWriter.startedOutcome`（新只读事务）重读。MySQL 可重复读下事务的读快照在第一次 SELECT
时就定了，事务内 catch 后重查看不到赢家刚提交的行；而 H2 合同测试是 READ COMMITTED，事务内重读
照样绿，这个差异必须在结构上避开。

## 考虑过的替代方案

- **Redis SETNX + TTL**：清单里的标准做法，但 TTL 与「审批永久存在」不匹配，窗口外的重放又
  会落成第二条；且偏离仓库「唯一约束兜底」的先例（`uk_oa_attachment_storage_id`、
  `uk_oa_process_cc_task`）。
- **全局唯一键（不带 `user_id`）**：同键不同用户时，后到的人要么读到别人的审批 id，要么收到
  一条与内容无关的拒绝；按用户唯一后查重条件与索引完全同形，不需要额外授权判断。
- **独立幂等表** `(key → process_id)`：两写一并、每次发起多一次关联，而这条记录的存在期与审批
  完全一样长，没有对齐问题。
- **复用 `attachmentDraftId` 当键**：见上，会让重新发起退化成静默不提交。
- **内容不一致时返回 201**：同一键代表同一次提交，返回「没发起」会让用户再点一次，反而制造
  重复；客户端在 `sending` 阶段已冻结快照，同键不同内容只可能是客户端异常或伪造。
- **响应体带上审批 id**：改动所有调用方都在用的响应形状，只为测试断言；验收继续用「已发起只
  多一条」更贴近产品保证。
- **通用 `Idempotency-Key` 请求头 + 全局拦截器**：目前只有发起是「每调一次就多一条要人处理的
  对象」；处理审批以 `taskId` 为天然键（重复 complete 被 Flowable 拒绝），发布有发布锁与状态机。
  将来真需要通用时，从请求体字段升级成拦截器是纯增量。
- **顺带把上传登记也做成幂等**：`storage_id` 是服务端每次 `createUpload` 新生成的随机值，唯一
  索引只保证「一行一个 id」；重试会多一条 pending 登记，但绑进审批前由定时清理回收，不会变成
  第二条审批。本轮只把这条契约写清。

## 后果

- 旧客户端与现有测试不带键时行为不变（唯一索引允许多个 NULL，MySQL 与 H2 皆然）。
- 输家的插入在 InnoDB 上会阻塞到赢家提交或回滚：赢家提交后输家拿到重复键，新事务重读拿到完整
  行（含 `process_instance_id`）；赢家回滚则输家的插入直接成功，不会两边都读空。极端情况下会
  先撞锁等待超时，按普通业务失败返回 201，由客户端按「发起结果待确认」处理。
- `oa_process` 没有删除路径，逻辑删除的行不会长期占用某个键；将来若引入删除，需要同时处理键
  的归属。
- 回归锚点：`ApprovalContractTest`（串行重读、并发唯一键、不同用户、不同键、非法键、内容不同
  仍返回第一条）、`FlywayMigrationContractTest`（V105 列存在）、接口套件
  `tests/api/d-work.spec.ts` D2b（同键并发两次，已发起只多一条）。
