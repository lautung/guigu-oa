# 改密作废该用户全部会话，令牌带用户行的 token_version

#143 复现出一个 S3：管理员把某用户的密码改掉后，改密前签发的 access token 在剩余 2 小时内继续可用，
7 天有效的 refresh token 也照样换新令牌；旧口令登录已被拒（208），会话却没有终止。
#134（ADR 0022）只补了退出路径：`TokenRevocation.revoke(sessionId)` 按一次登录作废，因为
GLOSSARY 的「退出」明确不作废全端会话。改密不同——旧口令已经失效，凭它换来的每一次进入结果
都应当一起失效，这正是 ADR 0022 拒绝用户级版本号时不适用于退出的那个场景。

`sys_user` 增加一列 `token_version`（V102，`BIGINT NOT NULL DEFAULT 0`，存量行补 0；迁移号跳到
102 是因为演示栈的 V100/V101 已经落库，新号低于它们会触发 Flyway 的 out-of-order 校验失败）；
`SysUserController.updateById` 用 `passwordEncoder.matches` 判定请求确实换了口令（带口令且与库里的
哈希不匹配，同一口令重复提交不算）时，调用 `SysUserService.changePassword`（由
`SysUserMapper.changePassword` 执行一条
`UPDATE sys_user SET password = ?, token_version = token_version + 1 ...`）——新哈希与递增后的
版本在同一条语句里落库，要么都成功，要么都失败；递增读的是行里的当前值，并发改密不会丢一次。
`SysUser.tokenVersion` 标成 `updateStrategy = NEVER`，任何实体级 `updateById`（包括登录时的
MD5→BCrypt 升级）都不会把读到的旧版本写回去，这一列只由上面那条语句推进。同一个 controller
里的普通资料更新也不再写 `password` 列（改密语句是它唯一的写入口），否则一次并发的资料编辑会把
改密前读到的旧哈希写回，让旧口令重新可用；`update_time` 由服务端补，保证只有 id 与口令的请求
仍能生成合法的资料更新。
access/refresh 令牌都带 `tokenVersion` claim：登录用认证时读到的那份用户快照写进令牌，
`TokenAuthenticationFilter` 与 `IndexController.refresh` 重新读到用户行后比较 claim 与
`token_version`，不一致按认证失败返回 `body.code=208`。没有该 claim 的令牌读作 0：部署前签发的
令牌继续有效，直到该用户下一次改密；存量行补 0 后与它一致，不需要一次性踢掉所有在线会话。

版本放在用户行而不是 Redis，是因为要跟口令写在同一个原子边界里。先写 Redis 再改库，改密失败会
白踢会话；先改库再写 Redis，Redis 失败会留下“口令已换、旧令牌仍可用”的 500——这正是要堵的洞。
放进同一行后没有第二次写入，也没有新的失败次序。登录也不再有竞态：令牌的版本来自认证口令时
读到的同一份行快照，管理员在认证过程中改密只会让这份快照的版本变旧，令牌签发后立即被拒；
如果认证发生在改密提交之后，旧口令本身就已失败。过滤器与 refresh 本来就要按用户名/id 读一次
用户，比较版本不增加查询；`SysUser.tokenVersion` 标 `@JsonIgnore`，用户接口的形状不变。

`UserDetailsServiceImpl.updatePassword`（登录时把旧 MD5 哈希升级为 BCrypt）不推进版本：它是
存储格式升级，不是用户换口令。它走实体级 `updateById`，而 `token_version` 的更新策略是 NEVER，
所以它不会把登录快照里的旧版本写回去，也不会与改密的递增互相覆盖。

否决的替代方案：按用户维护 sessionId 集合，改密时逐个 `revoke`——要新增登录期登记与集合清理，
集合 TTL 一旦短于 refresh 的 7 天寿命，最后一笔 refresh 就漏网，而且每次登录都写一份索引。
用 Redis 的用户级计数器——接口更小，但破坏了上面那条原子边界，计数器本身也没有和口令同生共死
的理由。用令牌 `iat` 与改密时间戳比较——JWT 的 NumericDate 只到秒，同一秒内“先登录后改密”与
“先改密后登录”无法区分：放宽一秒会漏掉旧令牌，收紧一秒会误杀改密后的新登录。用户级版本号由
退出共用——会把其他设备一起踢下线，违背 ADR 0022 与 GLOSSARY「退出」，所以版本只由改密推进。

代价：一次 Flyway 迁移（MySQL 与 H2 合同测试同一条）；`SysUser` 多一个不对外序列化的字段；
令牌格式多一个 claim，测试里直接签发的令牌要显式给版本（0 表示尚未改密）；管理员改自己的密码
会让手里这一台也立即失效，下一次请求落到登录页——这是“该用户全部会话作废”的预期结果，不是
缺陷；客户端无需改动，现有的 208 处理会清理本地进入结果。守卫：HTTP 合同钉住“只改资料不吊销、
改密后旧 access/refresh 都 208、只影响该用户、新口令签发的新令牌可用”；`SysUserController`、
`JwtHelper`、登录过滤器与鉴权过滤器的单元用例分别钉住版本推进、令牌携带与比较；接口套件 B5
从“已知缺陷”改为断言 208。
