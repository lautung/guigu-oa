# 数据范围解析成参数进查询，不用 SQL 片段拼接

若依的数据范围用 `@DataScope` 把可见范围拼成 SQL 片段（`params.dataScope`），Mapper XML 用 `${}` 直接展开。那套做法把授权值变成 SQL 文本，注入面、可测性与数据库方言都跟着走，本项目不采用。数据范围又要覆盖四个带部门归属的列表：用户、操作日志、登录日志、审批实例查询。

决定：

- 数据范围是角色上的一档：**1 全部 / 2 自定部门 / 3 本部门 / 4 本部门及以下 / 5 仅本人**。多角色按并集合并；`super_admin` 用 1（全部），不做身份旁路。
- 只作用于四个查询：**用户列表、操作日志、登录日志、审批实例查询（按发起人部门）**。部门/岗位/菜单/角色/字典/参数/公告/监控这些组织自身配置不套；办事四种列表与审批详情不套（成员资格已经是更强的可见性真相）。
- 解析结果是一个值对象：`unrestricted` / `visibleDeptIds` / `selfOnly + userId`。解析器读角色、`sys_role_dept` 与部门 `ancestors`，在服务层完成；每次请求解析，不新增缓存（表小，失效路径沿用权限缓存）。
- 查询侧只接受参数：MyBatis-Plus 用 wrapper 的 `in` 条件；手写 XML 用 `#{}` 绑定 + `<foreach>`。**禁止** `${params.dataScope}` 一类的片段展开。每个查询自己回答「本人列」是哪一列（用户 = id，日志 = 操作人，审批 = 发起人），解析器不猜业务列。
- 「自定」只来自 `sys_role_dept`；「本部门及以下」用部门 `ancestors` 前缀匹配；部门被删/停用时按当前树解析，不做历史快照。
- 范围解析不出任何可见部门且不是「仅本人」时返回空集，不是全部；管理员靠 `data_scope=1` 拿全部，不靠角色为空。
- 数据范围不进前端：`/info` 不返回它，客户端不做行级过滤。

考虑过的替代方案：

- **RuoYi 的 `${params.dataScope}`**（否决）：注入面 + 不可测 + 方言绑定。
- **MyBatis 拦截器全局改写 SQL**（否决）：隐式、难测，且会作用到不该作用的手写查询。
- **在 service 里逐个 if 拼 wrapper**（否决）：解析规则会散到四个查询，五档语义各写一遍。
- **给审批列表也套数据范围**（否决）：与成员资格模型冲突，同一行会有两套可见性真相。

后果：

- 四个查询各加一个 scope 参数；XML 增加 `<foreach>`；用户/日志/审批实例的列表合同测试按五档 + 多角色并集补用例。
- 审批实例查询要 join 用户/部门才能按发起人部门过滤；行形状与存活过滤（ADR 0050）不变。
- 现有 ADR 0009/0018 的列表读收口不变：scope 作为查询参数在 `toRequest` 里带上即可。
- 按钮点（ADR 0052）管动作，数据范围管行，两件事不混。

Related: ADR 0011/0045（成员资格与审批读）；ADR 0009/0018（列表读）；ADR 0050（手写 SQL 存活过滤）；ADR 0052（权限三层）；issue #208。
