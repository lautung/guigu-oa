# 审批第一波动作收成一个动作层，加签自建任务，撤回立状态档

蓝图 2.0 的 W1 要求转办、前/后加签、撤回、催办在栈上可用，并明确成员资格、待处理、已处理、发布证据四条合同随之修订（#267/#268）。研究 #269 把可行面收窄了：Flowable 8 没有加签与催办原语；转办 `setAssignee` 会覆盖 `ACT_HI_TASKINST.ASSIGNEE_`，原处理人可能连详情都读不到；撤回=结束运行时实例，历史落 `STATE_=cancelled`；或签销毁的剩余任务仍留在历史里。本仓现状是单任务线性模型：`ApprovalMembership` 只有申请人/当前处理人/历史处理人/抄送人四种关系，当前处理人只认 `task.assignee`；待处理只查 `taskAssignee`；已处理谓词是「除『发起申请』外全算处理」；`oa_process.status` 只有 0/1/2/-1。本 ADR 定这批动作的语义、载体与四条合同的修订；动态审批人另见 ADR 0069。

决定：

- **动作集合的语义**（谁能做、何时能做、做完什么状态）：
  - **转办**：当前处理人把审批永久交给一个启用用户（不能是本人或申请人）。转办写转办动作记录；原处理人成为**转办经手人**，只读（能看详情与附件，不能处理、不能补传）；转办不改变审批状态，可以再次转办，不设「转回」动作，也不设目标接受态。
  - **前加签**：当前处理人指定 1..N 个加签人（不能是本人或申请人）；加签人全部通过后回到原处理人继续通过/拒绝。加签期间原任务保持活动但被**冻结**：原处理人仍可读、可补传，不能动作；任一加签人拒绝即整条审批拒绝。
  - **后加签**：原处理人的通过先记账（写通过动作记录），但引擎任务不完成；加签人全部通过后才完成当前节点并进入下一节点；任一加签人拒绝即整条审批拒绝（原处理人的通过记录保留）。
  - **多人加签全部通过**（会签口径），固定并行，不做或签、减签；加签人不能再加签；同一批次进行中不能再加签，前加签回到原处理人后可以再来一批。
  - **撤回**：仅申请人，仅审批中（status=1），任意时刻可撤回（含已有节点处理过）。撤回结束运行时实例，`oa_process.status` 记 **-2 已撤回**，写撤回记录；已处理行、附件与抄送保留；撤回不可恢复，重新提交是另一次审批。不做审批人撤回自己已同意的处理。
  - **催办**：仅申请人，仅审批中；同一审批 **24 小时内最多 1 次**；对象是当前全部处理人（含未认领的候选人）；写催办动作记录，不改审批状态、不发通知、不进任何人的已处理。
- **载体**：加签不注入 BPMN、不改已发布产物——新增**加签任务表**与引擎任务配对（类型/批次/加签人/状态），前加签以冻结原任务表达「等待加签人」，后加签以「已记账未完成」表达；加签任务拒绝时对配对引擎任务走 `rejectToEnd`。撤回经 `ApprovalEngine` port 新增的取消方法结束运行时实例。新动作的写入口仍收在 `ApprovalWriter`（ADR 0012），校验先于写。
- **账本与状态**：`oa_process_record` 增 `action_type`（INITIATE/APPROVE/REJECT/TRANSFER/ADD_SIGN/URGE/WITHDRAW，留扩展位）与 `target_user_id`/`target_user_name`；详情时间线统一读这张表。已处理谓词改为**白名单** `action_type IN (APPROVE, REJECT)`，取代 ADR 0049 的「除发起申请外全算处理」负匹配；历史行按 `description` 精确回填动作类型（发起申请→INITIATE、已通过→APPROVE、已拒绝→REJECT、其余→OTHER）。`oa_process.status` 扩 `-2 已撤回`；`current_auditor` 停用，等待文案继续由 `description` 唯一拥有。
- **成员资格（ADR 0011 修订）**：关系扩成五种——申请人；当前处理人（引擎 assignee、候选人、加签任务 assignee，前加签挂起时带「不可动作」标记）；历史处理人（**改为账本里留下通过/拒绝的人**，不再读引擎历史）；抄送人；转办经手人。`canRead`=五种；`canUpload`=申请人或当前处理人（含挂起中的原处理人）；`canAct`=当前处理人且未挂起；候选人处理即认领。
- **待处理读（ADR 0045 修订）**：三源合成——引擎 assignee、引擎候选人（`taskCandidateOrAssigned`）、加签任务；每人每审批一行。前加签挂起行保留在待处理并显示「等待加签人处理」、隐藏动作按钮；后加签原处理人通过后不再进待处理；候选人行显示「候选人之一，处理即认领」。行形状扩 `actionKind`、挂起标记与催办标记，仍由共享列清单唯一拥有；total 仍按合成行数。
- **待确认（ADR 0004/0008 修订）**：转办、加签、撤回沿用「结果待确认」（恢复记录扩动作维度，离开不撤销、核实后结束、不自动重发）；催办不建恢复记录（24 小时频控与幂等让重复提交收敛）；新动作的 201 一律「确定未提交」（状态、权限、目标用户合法性都在写前判定），超时/断网/5xx 才进待确认；不把新动作塞进 `status: 1 | -1` 通道。
- **第二波边界**：委托/委派（长期代理与临时委派）、超时自动处理、节点级会签/或签/依次配置、减签、审批人撤回都不进第一波；只留 `action_type` 的扩展位与加签任务表的类型列，不预建 API 或空实现。

考虑过的替代方案：

- **用 Flowable 多实例做加签**：`addMultiInstanceExecution` 只对已经是并行多实例的活动有效，既有上传模板不满足；为加签强制把节点改成多实例要改 BPMN，违反 ADR 0003。
- **运行时改写 BPMN 插入节点**：把审批人与节点结构写进模型再恢复，等于让已发布模板在运行期变形，发布证据与恢复都对不上。
- **用 `delegateTask`/`resolveTask` 冒充加签**：委派是单任务临时换人、完成后交回 owner，表达不了前/后加签的「先审再回来」与「先同意再等签人」；`PENDING` 状态还不能 `complete`。
- **撤回用 `changeState` 跳到结束节点**：只是移动执行，并行/多实例残留时仍要兜底删除；`deleteProcessInstance` 才是取消语义，历史明确落 `cancelled`。
- **撤回后回到草稿可改再提交**：审批不是单据，重提就是新的一次审批；草稿态属于业务单据域（ADR 0066）。
- **转办后原处理人完全不可见**：引擎会把 assignee 覆盖成新人，原处理人连详情都会 403；至少要保留只读关系。
- **加签按或签（任一人通过即可）**：加签人是原处理人显式指定的，产品语义是补充会签，不是抽签；或签属于第二波节点配置。
- **已处理继续用「非发起申请」负匹配**：新增动作记录会被全量误收；动作类型显式白名单是唯一稳定谓词。
- **每个动作独立表**：时间线要 union 多张表，读模型与迁移都更复杂；一张账本 + 类型列足够。
- **预建委托/超时的接口与表**：没有语义的占位会先固化错的形状；只留扩展位。

后果：

- 合同修订落地：ADR 0004/0008/0011/0012/0043/0045/0049 按上述口径修订（各 ADR 已留修订注记），ADR 0003/0046 的发布证据修订见 ADR 0069。
- 用户可见：详情多四个动作（按成员资格出现）；待处理多「等待加签人/候选人/已催办」状态；已发起多「已撤回」；时间线出现转办/加签/催办/撤回记录。
- 读路径：待处理从引擎单源变三源合成，已处理从负匹配变白名单；转办经手人与挂起原处理人的可见性进入成员资格。
- 数据：`oa_process_record`、`oa_process.status`、加签任务表、模板节点规则表、`sys_dept.leader_user_id` 五处迁移；历史动作类型精确回填。
- 测试面：合同测试新增转办可见性、前/后加签、多人加签全通过、撤回状态与保留、催办频控、候选人认领并发、已处理白名单与时间线；H2 合同 schema 随迁移同步。
- 未做：委托/超时/节点级会签或签/减签/审批人撤回。
