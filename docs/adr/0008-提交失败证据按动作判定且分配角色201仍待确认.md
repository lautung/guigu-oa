# 提交失败证据按动作判定，分配角色的 201 仍待确认

客户端四个写入动作（发起审批、处理审批、保存模板、分配角色）的“确定未提交 / 可能已提交”由同一个纯函数 seam `classifySubmissionFailure(error, action)` 判定，各适配器只把两种结论映射到自己的恢复动作与文案；判定读取 `RequestFailureDetail`，不读会丢掉 205 的 `BusinessRequestFailure.businessCode`，把 refresh 失败、HTTP 401/403 与动作相关的业务码视为确定未提交，把超时、断网、5xx、未知与非法响应视为可能已提交。唯一按动作不同的是 201：发起、处理、保存模板的 201 都在事务回滚或写入前发生，分配角色的 201 却可能来自提交后的权限缓存失效、角色行已经提交，所以前者算确定未提交、后者仍按待确认，并由服务端合同测试 `PermissionCacheAfterCommitFailureTest` 钉住这个保证。保存模板因此收到 201/403 时恢复正常重试；新增写入动作必须显式给出行与证据，不能默认套用。

2026-10-30 增注（#144）：`sysRole/doAssign` 现在在写入前校验 `roleIdList`，不存在或已删除的角色 id 会以 201「只能分配已存在的角色」拒绝整个分配，因此分配角色的 201 不再必然意味着行已提交——写前校验拒绝与提交后的缓存失效失败共用同一个 201。客户端对分配角色 201 一律待确认的分类保持不变：写前拒绝被保守归入待确认，代价是一次人工重新读取核实，不产生错误状态；`PermissionCacheAfterCommitFailureTest` 钉住的「缓存失效失败时行已提交」保证不受影响（合同测试使用的种子角色存在，不会触发新校验）。
