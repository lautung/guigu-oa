# 参数校验在 HTTP 边界用注解且失败沿用业务信封

全仓库过去没有 `spring-boot-starter-validation`，也没有任何 `@Valid`：必填判断散在 `ApprovalWriter`、`AttachmentService`、`SysUserController` 与各 service 里，同一个「必填为空」在不同接口分别得到 401+208、403 或 201，文案也各写各的；模板 `formProps` 里的 `$required` 只在浏览器生效（#148）。

决定：在 HTTP 边界用 jsr303 表达静态形状约束，失败仍走现有业务信封——HTTP 200 + `code=201` + 具体中文消息，不给校验单独发明 HTTP 状态或业务码。登录是例外：它不经过 MVC，继续 401 + `code=208`（停用仍走 209）。

本轮覆盖：

- `ProcessFormVo.processTemplateId` 必填（`@NotNull`）。`formValues` 要求「合法 JSON 且 `formData` 是对象」，空值仍允许；这条在 `ApprovalWriter.startUp` 里判，和幂等键同处，`DemoScenarioSeeder` 这类直接调用方也受保护。
- `ApprovalVo.processId`、`taskId` 必填。它们过去落到 `requireCurrentApprover` 的 FORBIDDEN 分支，缺字段得到 403「无权访问」，与「无权」无关；现在 HTTP 路径先以 201 拒绝，`requireCurrentApprover` 的防御保留给直接调用方。
- `AttachmentUploadRequest.fileName`（非空、≤512）与 `sizeBytes`（非空、>0）迁到 DTO 注解；`AttachmentService.validateRequest` 只留 `contentType` 的 trim/默认值/格式、附件大小上限、草稿与成员资格。`contentType` 留在 service，是因为它先归一化再判合法，注解会在归一化之前误杀 `" text/plain "`。
- `LoginVo.username`、`password` 必填。`TokenLoginFilter` 自己读 JSON、不走 MVC，所以在过滤器里注入 `Validator` 手工校验；空体/畸形 JSON 一并收进来（过去抛出 `RuntimeException` 逃出过滤器，是容器级 500 面）。失败统一 401 + 208 + 字段消息，且在限流计数之前返回——空凭证不是密码猜测，不累计锁定期。
- `GlobalExceptionHandler` 增加两条分支：`MethodArgumentNotValidException` → 200 + 201 + 违反项消息（按字段名排序、`；` 连接）；`HttpMessageNotReadableException` → 200 + 201 +「请求体格式无效」。
- 不动的：`ApprovalWriter` 的幂等键判断（ADR 0032 的写入不变量）、`PageWindow`（全列表共用，文案被 `PaginationLimitContractTest` 钉住）、各 service 的领域/状态判断。

## 考虑过的替代方案

- **校验失败回 HTTP 400**：只给校验真实状态码，会让同一类请求形状错误出现两套约定——参数类型不匹配与畸形 JSON 仍是 200+201。要 4xx 就该一次收口所有请求形状错误，那是另一个议题；#145 只把容器级 404/405 还原成真实状态码，本轮沿用同一取舍。
- **给校验一个新的业务码（如 body 里 400/422）**：客户端只对 201/208/209/403 保留 `businessCode`，新码没有消费者，能区分的只有消息。
- **继续在 service 手写判断**：现状就是这样，同一个必填为空得到 403/201/401+208 三种结果；注解把静态形状集中到 DTO，service 只留领域判断。
- **把登录搬回 MVC 控制器**：登录在过滤器里先于 MVC 完成 401+208 与限流，搬走会重排整个认证契约，收益只有「能用 `@Valid`」。
- **`formValues` 写成自定义 jsr303 约束**：需要给 `model` 引入 jackson-databind，而且这条规则属于发起写入的领域不变量，和幂等键放在一起更合适。
- **配置类实体（`SysUser`/`SysMenu` 等）一起加注解**：`@Valid` 在方法调用前解析，先于 `@PreAuthorize`，会把「未授权 + 畸形体」从 205 变成 201；顺序问题留给 #152。

## 后果

- 线上响应形状变化：缺必填字段从 403（approve）、泛化 201（startUp 空模板）或 401+208（登录空值）收敛为 201 或 208 + 具体消息；客户端本就把 201/208 当业务失败提示，不需要改。
- 登录空体不再落到容器层；空凭证与畸形 JSON 不累计登录失败次数。
- `AttachmentService` 的直接调用方不再经过 fileName/sizeBytes 形状校验；`createUpload(user, null)` 的空请求保护保留，`AttachmentServiceTest` 里那批形状用例改为 HTTP 合同测试。
- 校验先于 `@PreAuthorize` 的顺序在本轮不成问题——覆盖的四个 DTO 都不在 `@PreAuthorize` 路由上；#152 落地时必须先定顺序。
- 未做：动态表单必填（#153）、参数类型不匹配的文案与状态码、客户端 form-create 与登录页的本地规则（保持不变，服务端只补一层）。
- 回归锚点：新增 `RequestValidationContractTest`、`LoginAuthContractTest`（空凭证）、`AttachmentServiceTest`（收缩后）、`PaginationLimitContractTest`、`HttpErrorSemanticsContractTest`、接口套件 `tests/api/`。
