# 业务单据按业务键关联审批，终态在同事务内幂等回写

ADR 0066 把业务单据与审批分成两态，但只钉了方向（回写单向），没定关联形状：`oa_process` 没有业务键，`oa_attachment` 只认审批实例，人事、考勤、报销三个域（W2–W4）都卡在同一个问题上——单据提交时怎么起审批，审批终态怎么回到单据，详情页怎么把两者拼起来。研究 #270 已确认 `oa_process` 无 business key、`oa_attachment` 不能独立于审批长期归档；蓝图 2.0 §5.7 把形状留给了本票。

决定的落点是「一张单据、多次审批、一个端口」：审批行用业务键指向单据，端口只在 process 模块一侧定义，业务域实现回调；回写与审批动作同一事务；撤回档位留给 #271，业务端口只讲三分类。

## 决定

### 关联键与基数

- `oa_process` 增加两列：`business_type VARCHAR(64) NULL`、`business_id BIGINT NULL`，联合**普通**索引 `(business_type, business_id)`。不加唯一索引，也不建独立关联表。
- 值域 `<域>.<单据>`（蓝图 §5.7）：`hr.transfer`、`hr.resign`、`attendance.leave`、`attendance.overtime`、`expense.claim`；通用审批两列为 NULL。
- 一张单据可积累多次审批：拒绝/撤回后可**重新提交**，起一条新审批，单据号不变；同一时刻最多一条进行中。通过后不再接受重提，要改另立新单（变更单不在本波）。
- 单据表**不存** `process_id`；详情按 `(business_type, business_id)` 回查最近一条审批，避免指针与账本漂移。

### 发起与回写的缝

- 端口在 process 模块：`BusinessApprovalStarter`（业务域调用）与 `BusinessApprovalCallback`（业务域实现，按 `businessType` 注册）。`ApprovalWriter` 仍是唯一写入实现（ADR 0012），业务发起复用它的次序、事务与 `(user_id, idempotency_key)` 幂等索引（ADR 0032）。
- 业务域依赖 process，process 不依赖业务域：process 只认端口，不引用任何 `hr`/`attendance`/`expense` 类型。
- 业务发起**必须**带客户端生成的幂等键；缺失、空白或超长按 201 拒绝（与通用审批「缺省不去重」不同，业务单据的重放代价更大）。同一单据的并发提交：同键按 ADR 0032 重放；不同键由单据状态 CAS 拒绝（「单据已在审批中」）。
- 发起时校验 `businessType` 有已注册回调，没有回调按 201 拒绝——不允许造出一条「结束也没人回写」的审批。
- 回调在审批动作的同一事务内、账本更新之后调用；业务域在自己的状态机上完成回写与域内副作用（异动记录、余额扣减等）。
- 端口只有三分类：`APPROVED` / `REJECTED` / `WITHDRAWN`。`oa_process.status` 的数值与撤回档由 process 映射，#271 怎么定撤回档都不影响业务端口。

### 生命周期

- 单据先落**草稿**；提交 = 状态 CAS（草稿/拒绝/撤回 → 审批中）+ 起审批，同一事务。
- 终态映射：`APPROVED` → 通过、`REJECTED` → 拒绝、`WITHDRAWN` → 撤回；中间节点（还有下一任务）不回写单据。
- 审批中不可删单；标题、展示快照与附件在提交时定稿，之后改单据不影响在途审批。
- 超时不在本波（章程 Q7 第二波），单据不设超时档；将来加也必须是显式动作回写，不由读侧推断。
- 各域状态文案自定（ADR 0066），但终态三分类固定；域内实现票必须给出自己的状态机与回写点。

### 失败与幂等

- 账本更新 + 流转记录 + 单据回写同一 DB 事务，任一失败整体回滚。
- 引擎命令仍是外部副作用：「引擎已提交而 DB 回滚」的缝隙沿用 ADR 0012 的既存边界，业务域不新增 outbox 或对账机器。
- 回调必须幂等：并发终态（撤回与通过竞态；将来或签同理）可能让两个动作都判定为终态。同值终态 = no-op 成功；不同值 = 抛错并回滚整个动作。

### 模板关系

- 共享映射表 `oa_business_template(business_type PK, process_template_id)`；迁移为每个业务类型种子一行。提交时按业务类型解析，仍走 ADR 0003 的发布证据（`resolveForInitiation`）。
- 模板未发布、证据失效或映射缺失 → 发起 201 拒绝，单据留草稿。
- 升级 = 发布新模板 + 改映射；在途实例按已部署定义跑完（发布冻结），新提交用新模板。账本已快照 `process_template_id`，审批详情读的是发起时那份。
- 单据表不存模板 id；模板与业务类型的关系只有映射表一处。

### 读模型

- 办事五种列表**不排除**业务审批（它们就是审批，GLOSSARY「已发起」= 该用户发起的审批）；域内列表（我的报销单/我的申请）另出单据视角。审批行形状加 `businessType` 供前端标来源。
- 审批详情展示**提交时快照**：process 侧把摘要写成 `form_values` 的 `formShowData`（现有详情页渲染路径），票据等附件照旧挂 `oa_attachment.process_id`、审批成员可下载（ADR 0011）。审批人**不因**业务单获得业务后台页权限。
- 单据详情返回单据 + 审批摘要（`processId/status/当前审批人/起止`），不嵌完整审批载荷；点进审批详情走现有详情页与成员资格 gate。
- 后台审批实例查询包含业务审批，行形状加 `businessType/businessId`（可空）；本波不做按业务类型筛选。

## 迁移草案（不执行）

```sql
ALTER TABLE oa_process ADD COLUMN business_type VARCHAR(64) DEFAULT NULL;
ALTER TABLE oa_process ADD COLUMN business_id BIGINT DEFAULT NULL;
CREATE INDEX idx_oa_process_business ON oa_process(business_type, business_id);

CREATE TABLE oa_business_template (
  business_type VARCHAR(64) NOT NULL,
  process_template_id BIGINT NOT NULL,
  create_time DATETIME DEFAULT NULL,
  update_time DATETIME DEFAULT NULL,
  is_deleted TINYINT NOT NULL DEFAULT '0',
  PRIMARY KEY (business_type)
);
```

按 #185 的教训，索引建完要用实发 SQL 验执行计划（详情查询是 `(business_type, business_id)` 等值 + 按 id 倒序取一条）；H2 合同测试跑真迁移，写法保持 MySQL/H2 双兼容（`CREATE INDEX` 而非 `ALTER TABLE ... ADD INDEX`）。

## 考虑过的替代方案

- **一单一审批，重新发起复制新单**：`(business_type, business_id)` 可加唯一索引，完整性最强；但报销改票重提、请假改期重提都会在「我的报销单」留下多张同源单，单据号失去意义。
- **独立关联表 `oa_process_business(process_id UNIQUE, ...)`**：多一次 join，只换来「一条审批最多一条关联」这一个约束；在「一单多审批」下换不来「同时一条进行中」。
- **单据表存 `current_process_id`**：列表读快，但指针与账本双写会漂移，正是 ADR 0066 要避免的两态合一。
- **靠可空列或生成列做部分唯一索引钉「一单一条进行中」**：MySQL 与 H2 的写法与语义都要各验一遍，而单据状态 CAS 已经是同一条约束且更早拒绝；价值密度不抵一份双库差异。
- **领域事件（`ApplicationEvent` + `@TransactionalEventListener`）做回写**：更松，但「谁没实现」「顺序」「回滚」都要在事件层重讲一遍；端口是编译期可数的。
- **新 `lautung-oa-business` 接口模块**：process 与三域都依赖它，最干净；但 ADR 0012 刚定过「不提前抽端口，等第二个消费者再拆」，现在拆只多一个模块与一层依赖。
- **每域自己的模板配置表 / 模板上挂 `business_type` / 发起时用户选模板**：分别是三份重复校验、一份模板绑死一个业务类型、产品上不成立。
- **outbox/事件表 + 定时对账**：小团队栈没有消息面，`sys_job` 能跑但维护两套终态真相；ADR 0012 已明确不建补偿机器。
- **读时自愈（打开审批中单据时查引擎真相修状态）**：把复杂度塞进每个读，且改掉 ADR 0012 的写侧边界。
- **审批详情嵌完整单据 / 办事列表隐藏业务审批 / 审批人走业务页读单据**：分别是对域模型两次授权、用户找不到自己发起的审批、违反「办事登录即有」。

## 后果

- 蓝图 2.0 §5.7 的「形状留 #272」由本 ADR 收口；§8 的 W1 实现票可直接按本 ADR 拆。
- ADR 0066 的「幂等键形状由 #272 定」由本 ADR 落定：业务发起键 + 单据状态 CAS + 回调幂等三件套。
- 三个域的实现票（#273/#274/#275 及其后续）必须给出：状态机、`businessType` 常量、回调实现、模板映射种子、列表与详情的读形状。
- `oa_process` 的写入口仍是 process 模块；业务域只经端口，不直接写账本。
- 附件：审批附件继续挂 `oa_attachment.process_id`；单据级长期附件（人事合同等）不属本 ADR，ADR 0002 修订由 W4 报销承接。
- 未决：撤回档数值（#271）；业务单据的域内字段、状态文案与列表列（各域票）。
