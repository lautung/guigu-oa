# 已处理行单位是审批，读证据由账本动作记录供给

规格 #178 的 Out of Scope 欠账（#186）：已处理列表的行单位是已完成任务（引擎历史任务行），
同一审批处理过两个节点的用户看到重复行，total 计任务数；而 GLOSSARY「已处理」一直是审批粒度
（「该用户已经处理过的审批」），「审批」词条明确待处理/已处理/已发起都指向同一次请求——现行行为
与词条冲突，且由 `ApprovalContractTest` 的同人两节点场景合同钉住。另一侧，「谁处理过哪条审批」
的动作流水 `oa_process_record` 由唯一写入口 `ApprovalWriter` 逐动作写入（发起申请、已通过/已拒绝，
ADR 0012），去重的原始数据在账本里现成有。

决定：

- 行单位=审批（GLOSSARY 口径）：同一审批处理过多个节点只出一行；total=去重审批数
  （`COUNT(DISTINCT process_id)`，与抄送我的同口径）。
- 已处理读证据从引擎历史切换到账本动作记录：`LedgerApprovalListReader.processed` 改调
  `OaProcessMapper.countProcessedRows/selectProcessedRows`（原生 LIMIT/OFFSET，#122 口径），
  处理动作记录按审批去重、最近一次处理时间倒序、同刻由审批 id 决胜（#179 口径）。「发起申请」
  流转记录不算处理：它与动作记录共享 status=1，只按文案排除，文案立成
  `ProcessApprovalSupport.INITIATION_DESCRIPTION` 常量、writer 与 reader 同源（record 表描述值域
  由 V107 一类的订正迁移维护）。负匹配对 NULL description 行为假（列可空）——写口恒非 NULL，
  仅手改数据可触发，属已知边界不另设防。
- 这是对 ADR 0045「待处理/已处理保持引擎分页」中已处理一半的替代：待处理仍由引擎分页（任务创建
  时间倒序 + 任务 id tiebreaker），已处理不再消费引擎历史——`ApprovalEngine.processedTasks/
  processedCount/ProcessedTask` port 与 `ProcessEngineApproval` 同名 helper 删除（影子删除，
  ADR 0021 先例），cutover/引擎单测的 processed 断言随之裁剪；引擎历史只服务成员资格证据
  （`hasHistoricAssignee`，ADR 0011）。行形状 owner 仍是 `OaProcessMapper.xml` 共享列清单
  （已处理行从按实例 id 回查改为直接 include，`selectRowsByInstanceIds` 删除）。
- 供给换轨不换门：五列表仍走 `ApprovalListReader` 唯一入口（ADR 0045），行形状 `ProcessVo` 不变、
  响应包封不变。用户可见变化=重复行消失、total 变小、排序锚点从「任务分配时间」变为
  「最近一次处理时间」。
- `oa_process_record` 补 `(operate_user_id, process_id)` 复合索引（V109，CREATE INDEX 双兼容写法：
  H2 合同测试跑真迁移，MySQL 专有 `ALTER TABLE ... ADD INDEX` 会在 H2 上炸）——#185 教训：建后必须
  用实发 SQL 验证执行计划，索引建了不等于优化器会用。
- 行查询的**形状纪律**（EXPLAIN ANALYZE 取证，证据 `docs/test/evidence/2026-11-01-perf-processed-dedup/`）：
  窗口必须收在派生表内、先只聚合 id，载荷 join 只碰当页行。初版把窗口放外层，17k 分组全体做
  四表 PK 回表后再排序，findProcessed p95 150→383ms（唯一回归动作，其余七个动作持平）；改形后
  单条 63.1→26ms，p95 回落 304ms（before 151ms，判定线 500ms）。count 侧保留与抄送计数同形状的
  `COUNT(DISTINCT)`+join+is_deleted（37.5ms，total 与行查询语义一致）；压测全程慢 SQL 无业务语句，
  总吞吐与 before 持平。med 残差（114 vs 79ms）来自对该用户动作记录的全量去重聚合，属换供给固有成本。

## 考虑过的替代方案

- **引擎适配层去重（port 语义改成「处理过的审批」）**：Flowable 历史查询无 group by，分页正确的
  DISTINCT 要么对 `ACT_HI_TASKINST` 发原生 SQL（把引擎内部表当读模型，ADR 0045 已拒绝该方向），
  要么 port 加字段后 read module 内多取页去重（复杂度不可控）。
- **页内去重（read module 拿当页任务后 distinct）**：改动最小，但页大小缩水、total 仍是任务数、
  同一审批可跨页出现，三处语义欠账。
- **正匹配排除发起记录（`description IN ('已通过','已拒绝')`）**：处理文案变更时静默漏行；
  负匹配只依赖「发起申请」一个常量，而文案变更历来走订正迁移（V107 先例）。
- **给 `oa_process_record` 加记录类型列**：最干净，但为一个查询谓词加列+迁移，价值密度低；
  将来有按类型查询的需求再加不迟。
- **count 去 join（去掉 `a.is_deleted` 回表验删）**：可省 17k 次 PK 回表约一半 count 成本，但旧供给的
  total（引擎任务数）本就不排除已删审批，改了反而引入 total/行语义分歧；且无生产路径软删审批，
  17ms 级收益不抵语义含混。
- **反连接取「每审批最新一条记录」替代全量分组聚合**（扫到当页即停）：页查询可降为 O(页×探针)，
  但 tie 语义、is_deleted 过滤的正确性细节成倍增加，而 count 的全量聚合（地板）仍在——整体复杂度
  换不来量级收益，不取；若将来 count 成本真成为瓶颈，从这里起步。

## 后果

- 合同缝改钉：`ApprovalContractTest` 已处理行单位钉住从「同人两节点重复出现」反转为「只出一行、
  total=1」；新增排序锚点钉住（时间压过 id 决胜、同刻 id 决胜反转顺序）；KeepPagination 的
  processed total=2 语义变为「两个不同审批」，已处理供给的窗口语义由它钉住。
- 读路径查询数：从「引擎历史任务分页 + 计数 + 按页回查」（两引擎一账本）变为两条账本 SQL，
  零引擎往返；V109 索引支撑按人扫描与分组。k6 对比（证据目录见上）：findProcessed p95 151→304ms
  （初版形状 383ms 已按实发计划改形修复，慢 SQL 全程无业务语句），总吞吐持平
  （175.6k vs 171.6k 请求）；客户端 525 单测与 e2e 零改动全绿。
- 待处理不动：线性流程同一审批同一时刻只轮到一个节点，行单位天然审批级；将来出现并行节点再另议。

**2026-11-06 修订（#271）**：已处理谓词改为 `action_type IN (APPROVE, REJECT)` 白名单，取代「除发起申请外全算处理」负匹配；转办、加签发起、催办、撤回不算处理；「历史处理人」证据同步从引擎历史换到账本。见 ADR 0068。
