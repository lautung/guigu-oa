# 配置路由按菜单授予统一 gate，种子账号不再例外

候选 7 的评审把服务端配置权限列为唯一的在发生提权：用户、角色、菜单、审批类型、审批模板、审批实例查询六组配置路由里，只有菜单与角色两组有方法级 gate，其余对任何已登录用户开放；同时 `SysMenuServiceImpl.findUserMenuEntities` 对 `userId == 1` 返回全部启用菜单，与 GLOSSARY「配置权限只来自被授予的配置类菜单，不因某个种子账号另开通道」直接冲突。

现在所有配置路由都走同一个方法级 gate：`@PreAuthorize("@configurationMenuGate.isGranted('sysUser')")` 这类注解放在六个配置 controller 的每个方法上，现有的 `@sysMenuServiceImpl.hasCurrentUserMenuAccess` 注解一并迁到该 facade；facade 只把「用户 + 菜单 path」交给 `SysMenuService.hasMenuAccess`。授予权威仍是菜单树：角色被授予至少一条配置类菜单，才算有该页的配置权限；页面级授予覆盖该页全部读写，不引入按钮/动作权限。`templateSet`、`assignAuth` 这类隐藏页认可见父级（`processTemplate`、`sysRole`），与前端 `configPermission` 的隐藏页语义一致；`/admin/process` 前缀下的办事路由（`api/ProcessController`）与认出路由（`IndexController`）显式豁免，不按前缀误伤。

拒绝形状沿用现有方法级安全：`AccessDeniedException` 由 `GlobalExceptionHandler` 映射为 HTTP 200 + 业务码 205，评审里的「403」只表示语义拒绝，不改变 wire contract。gate 每次直接查菜单授予，不新增缓存；配置页每次打开只有少量受 gate 请求，先保持失效简单。

`userId == 1` 的例外由一条幂等 Flyway V5 取代：新建普通角色「配置管理员」/`config_admin`，把全部配置节点（根、页面、隐藏页）授予它，再按用户名 `admin` 赋给种子账号；`user` 种子保持无角色。`findUserMenuEntities` 删除 `userId == 1` 分支，`PermissionCacheInvalidator` 删除 `SEED_ADMIN_USER_ID` 特判，只按角色成员失效；现有测试夹具的写死 id 1–3 改为 101+，清理按 `role_code`/username。代价是 admin 不再是代码里的特殊账号：新增配置菜单必须显式授予角色，admin 才会看到；这与「菜单树是授予权威」一致。

否决的替代方案：集中到 `SecurityFilterChain` 按前缀匹配会把 `/admin/process` 下的办事路由一起拦住；`ConfigurationAccess` 领域对象会引入 GLOSSARY 明确避免的 access-policy 词汇；把拒绝改成 HTTP 403 会改变现有客户端与测试依赖的 205 协议；按钮级权限与 GLOSSARY「授予到配置类菜单为止，没有按钮」冲突；菜单授予缓存会让失效路径与现有 Redis 权限缓存分叉。
