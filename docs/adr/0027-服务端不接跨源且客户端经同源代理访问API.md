# 服务端不接跨源，客户端经同源代理访问 API

#141 复现出一个 S4：`ProcessController` 上的 `@CrossOrigin` 让
`GET /admin/process/findPending/1/10` 对任意 `Origin` 回显
`Access-Control-Allow-Origin: *`，`OPTIONS /admin/process/approve` 的预检返回 200 并允许
`token` 请求头。当前鉴权用自定义请求头而不是 Cookie，攻击页面拿不到 token 就无法直接利用；
但把它留成既定配置，一旦将来改用 Cookie 会话或让第三方脚本持有 token，就升级成 CSRF。
安全基线记为 SEC-CSRF-02/03。

现在删掉 `ProcessController` 的 `@CrossOrigin`，并去掉 `WebSecurityConfig` 里空参数的
`.cors(...)`。`service-oa` 不再参与 CORS：既不回 `Access-Control-*`，也不替浏览器处理预检。
理由是同源本来就是产品的唯一访问方式——统一客户端由自己的 nginx 发出页面与静态资源，
`/dev-api` 在同一来源下反代到 `service-oa:8800`；开发态 Vite 也把 `/dev-api` 代理到 8800。
浏览器对 `service-oa` 没有任何跨源调用，服务端再声明 CORS 只会多一个可被误配的放行面。

跨源需求留给入口网关：如果部署把 API 放到另一个来源，由网关按受信来源列
`Access-Control-Allow-Origin`，并只允许实际用到的方法与请求头。不使用 `*`，也不把 `*` 与
自定义 `token` 头组合。演示栈里唯一的跨源请求是附件直传 MinIO，那属于对象存储自己的配置
（`MINIO_API_CORS_ALLOW_ORIGIN`），与 API 无关。

否决的替代方案：在 `service-oa` 配一份受信来源白名单——当前没有任何跨源消费者，白名单没有
可验证的用处，却留下一个以后被改宽的口子；保留 `@CrossOrigin` 只限制来源——控制器级注解按
处理器生效，新增控制器还会再开一次，不如删干净；只删注解但保留 `.cors(...)`——空参数会让
Spring Security 继续从 MVC 的跨源注解取配置，等于把同一回归留在原地。

代价：从另一个来源直连 8800 的浏览器脚本读不到响应（CORS 由浏览器执行，curl、node 等非浏览器
客户端不受影响）。这是有意的；受支持的访问路径只有同源代理。守卫放在三层：`CorsContractTest`
断言带恶意 `Origin` 的审批读取没有 `Access-Control-Allow-Origin`、预检不授予 `token` 请求头，
并拒绝任何控制器重新带上 `@CrossOrigin`、任何全局 `CorsConfigurationSource` 或
`addCorsMappings` 注册；安全扫描的 SEC-CSRF-02/03 在真实栈上复跑。
