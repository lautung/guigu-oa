# 会话核验收成一个 module，401 写出收进一处

第三轮架构审查（#173）核出的认证家族热区：`IndexController.refresh` 因为在匿名白名单上，把
`TokenAuthenticationFilter` 的四连核验（查吊销、加载用户+身份比对、token_version、查停用）原样
复制了一遍；401+208/209 的写出散在 4 个文件 9 处（按「HTTP 401 + 业务枚举」的拼写点计：过滤器 2、
登录过滤器 5、入口点 1、续期控制器 1——续期那一处是 `unauthorized()` 助手，一处拼写、被 4 个失败
分支调用），每处各自拼写「HTTP 401 + 哪个业务枚举」；`info` 还留着一个把 208 塞进 HTTP 200 信封的死
分支（info 不在匿名清单，到得了的请求过滤器必然已验过同一令牌头，分支不可达）。九天内
ADR 0022（退出吊销）、0023（登录失败限制）、0029（改密作废）、0037（refresh 失败家族）全落在
认证家族——重复与散点正好压在这条被反复修改的路径上。

决定：新增 `SessionVerifier`（`common/spring-security` 的 `security/session` 包）作为会话核验的
唯一实现（GLOSSARY「会话核验」），输入令牌与种类（ACCESS / REFRESH），输出封闭结果
`Recognized(claims, SysUser)` 或 `Rejected(208 凭证无效 | 209 账号停用)`。判定顺序冻结为
解析 → 吊销 → 良构 → 按用户名加载 → 身份比对 → token_version → 停用，两处调用方原有的顺序
原样保留；「版本先于停用」由 `SessionVerifierTest` 钉住。用户统一按用户名经
`UserDetailsService.loadUserByUsername` 加载（spring-security 里唯一的用户查询缝），refresh 从
`getById` + username 比对切换过来——用户名唯一（ADR 0042）后两种方向域上等价。

新增 `AuthenticationFailure` 枚举（`INVALID_TOKEN`→208、`ACCOUNT_DISABLED`→209）与
`AuthenticationRejections` 静态写出器（`security/response` 包），9 处 401 写点全收：过滤器、
入口点、续期控制器经 `write`/`entity`，登录过滤器的 5 处也改走 `write`，用消息覆写承载「过于
频繁」与字段校验文案，登录失败分类决策（ADR 0023）原样留在登录过滤器。`info` 删除死分支，改读
过滤器设置的 `LoginUserInfoHelper` ThreadLocal，不再重解析令牌；`logout` 的解析式吊销不属核验
（ADR 0022 故意接受过期凭证），保持原样。

核验之后的动作不进 module：过滤器保留 ThreadLocal 写入、Redis 权限加载与 Authentication 构建，
refresh 保留新 access 令牌签发（沿用 refresh 的 sessionId，ADR 0022 不变量）——module 只答
「这张凭证认不认得出这个人」。

## 考虑过的替代方案

- **module 也构建 Authentication（连权限缓存一起收）**：refresh 用不上 authorities，却让核验
  依赖 RedisTemplate；权限缓存是过滤器的关注点，不是核验的。
- **只收核验相关的 4 处写点，登录 5 处继续用 ResponseUtil**：「401+信封+枚举」的拼写知识仍留
  在两处，下次认证家族改动（如 0037 那样）还要两边同步。
- **refresh 继续按 id 加载**：要在 spring-security 新增按 id 查询的方法才能统一，而按用户名
  加载对每一行合同测试结果都相同。
- **info 也调 module 重新核验**：info 是最热的已认证端点（每次进应用都调），多一整套 Redis+DB
  核验只为覆盖一个不可达分支；改读 ThreadLocal 零成本。
- **只把 info 的死分支改成 401 写出**：保留死代码，最差。

## 后果

- 行为零变化：`LoginAuthContractTest`（401/208/209 全表、refresh 失败形状、畸形 JSON 200+201
  分界）、`HttpErrorSemanticsContractTest`、`RequestValidationContractTest` 原样保持绿；六层
  拒绝顺序（`docs/agents/server-modules.md`）与 `PublicApiPaths` 不动。
- refresh 路径新增的良构判断（username/userId 非空）在合法签名令牌上不可达
  （`JwtHelper.readClaims` 已强制 userId 为数值、sessionId 非空白），只是统一两处形状。
- 唯一未写进决定段的行为差异：过滤器在核验拒绝时额外 `SecurityContextHolder.clearContext()`——
  该请求点上下文本为空，可观察行为不变，属防御性清理（原实现只在停用路径清理）。
- 服务端测试 449 → 465：新增 `SessionVerifierTest`（14 条，钉每条拒绝原因与冻结顺序），过滤器
  单测改为对 verifier 打桩；`TokenLoginFilterTest` 断言响应内容，零改动通过。
- 下一处会话语义（如新的吊销原因、新的核验维度）只改 `SessionVerifier` 与
  `AuthenticationRejections` 各一处。
