# 状态切换与发布只用写方法，GET 路由移除

#138 复现出一个 S3：`GET /admin/system/sysUser/updateStatus/{id}/{status}` 返回 200 并把 `status` 改成 0；`GET /admin/process/processTemplate/publish/{id}` 同样由 GET 触发发布。浏览器预取、图片标签、日志重放和链接预览都会自行发出 GET，这两个入口等于让任何拿到链接的人在不经确认的情况下改状态或发布模板。安全基线把这两条记为 SEC-CSRF-04/05。

现在 `SysUserController.updateStatus` 只由 `@PutMapping` 承接，`OaProcessTemplateController.publish` 只由 `@PostMapping` 承接，路径不变。旧的 GET 路由直接移除，不保留只读别名：保留别名会让同一个动作有两个入口，客户端或脚本仍可能按老路径调用。移除后 GET 到不了写方法——`GET updateStatus/{id}/{status}` 没有处理器，DispatcherServlet 以方法不支持拒绝；`GET publish/{id}` 会落到同一前缀的分页读路由 `{page}/{limit}`，在参数转换时失败。两种结果都被 `GlobalExceptionHandler` 收成失败信封（HTTP 200、`body.code=201`），都不会改状态或发布。GET 仍只读：`get/{id}`、分页与 `findStartable` 都不改变状态。

方法按语义分开：状态切换是「把字段设成给定值」，重复同一请求结果不变，用 PUT；发布是一次动作，部署流程定义并写一条发布记录，不是替换模板资源，用 POST。这与仓库现有的写入口分组一致：`save`、`doAssign`、`approve` 用 POST，`update` 用 PUT。

客户端两个 module 随之改方法：`src/config/sys-user.ts` 的 `updateStatusRequest` 用 `method: 'put'`，`src/config/process-template.ts` 的 `publish` 用 `method: 'post'`，页面绑定不变。

否决的替代方案：把旧 GET 保留成只读——两个入口指向同一语义，客户端漏改时表现为「静默无效果」，比直接失败更难发现；两个动作都用 POST——状态切换是幂等的字段赋值，PUT 更贴近；两个动作都用 PUT——发布会写一条新的发布记录，PUT 暗示替换；在前端或网关拦 GET——服务端仍把写操作暴露在只读方法上，绕过客户端就直接命中。

代价：外部书签或脚本里的旧 GET 链接现在得到 `body.code=201` 的失败信封；客户端、e2e 造数助手与接口测试必须同步（已完成）。服务端在配置路由合同里新增一条按 handler mapping 的断言：两个动作只由写方法注册；另用一次 GET 请求证明 `updateStatus` 的方法不支持异常与状态不变。安全脚本的 SEC-CSRF-04 改为断言「GET 不再成功且状态不变、PUT 生效」，SEC-CSRF-05 改为断言两个动作的 mapping 分别是 Put 与 Post，SEC-JWT-08 与 SEC-GATE-01 里的调用同步改用写方法。
