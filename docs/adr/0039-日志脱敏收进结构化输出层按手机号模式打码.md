# 日志脱敏收进结构化输出层按手机号模式打码

`SysUser` 的 `phone` 与 `name` 明文存在,日志里出现这些值的地方没有任何脱敏(#150):登录审计(`Slf4jLoginAudit` 的 `username`——它可以是手机号)、校验异常栈(Spring 会把 rejected value 写进异常消息)、以及未来任何随手 `log.warn(user)` 的分支。日志进 CI artifact 与容器 stdout,手机号一旦进日志就等于离开受控存储。

决定:**打码收进结构化输出层,一个接缝覆盖所有 logger**。Spring Boot 4.1 的官方接缝 `logging.structured.json.customizer` 挂一个 `StructuredLoggingJsonMembersCustomizer`(`common/service-util` 的 `PhoneNumberMaskingCustomizer`),用 `JsonWriter` 的 `applyingValueProcessor` 把 `message` 与 `stack_trace` 两个成员经 `PhoneNumberMasker` 重写后写出:其余原样直通,手机号形状渲染成 `138****1234`。接线在 `application.yml`,dev/demo/prod 共用同一份配置。

- 覆盖的呈现形态:`1[3-9]` 开头的 11 位数字、`+86` 国家码前缀(`+8613800131234` → `+86138****1234`)、`-`/空格分隔的分组(`138-0013-1234` → `138****1234`)——`TokenLoginFilter` 的 username 直取用户输入,失败登录的审计行里可能出现任意形态。
- 打码发生在编码时而非事件上:appender 拿到的 `ILoggingEvent` 仍是原文,只有写出的 JSON 被重写,对日志管线其余部分零影响;MDC pair(`traceId`)不在处理范围内,直通。
- 数字边界护栏:12 位数字串、带前缀的数字串都不会命中,ids 与 token 不被误伤。
- issue 建议的 logback `conversionRule` converter 路线在本仓库走不通:`logging.structured.format.console: logstash` 下消息由 `JsonWriterStructuredLogFormatter` 直接写,不经过 pattern layout,自定义 converter 不会被调用。

## 考虑过的替代方案

- **在每个写日志的边界做格式化**(`Slf4jLoginAudit.field()` 里打码等):接缝数量等于未来日志语句数量,漏一处就漏一个手机号;异常栈里的 rejected value 也够不到。
- **logback `conversionRule` 自定义 converter**:只对 pattern layout 生效,本仓库 console 是 logstash 结构化编码器,消息字段不经过 pattern,converter 静默失效——最危险的一种失败(以为脱敏了,实际没有)。
- **同时打码 `name`(姓名)**:模式法识别不了任意文本里的姓名;要动就得在各写日志点知道「这个字段是姓名」,回到边界方案的接缝爆炸。响应体里的手机号脱敏是另一个决策(配置页要能编辑手机号),本条不顺手改。

## 后果

- 模式法只覆盖 CN 手机号形状;其他 PII(`name`)在日志里仍是明文,这是已知并接受的剩余面。
- 未来若新增结构化成员(或换成 ECS/graylog 格式),新成员若携带自由文本需把路径加进 `PhoneNumberMaskingCustomizer`;`message`/`stack_trace` 之外当前无自由文本成员。
- 若某天关掉结构化日志退回 pattern 输出,打码会随之失效(接缝挂在结构化编码器上);当前所有 profile 都走 logstash console,没有第二条输出路径。
- 打码是渲染层行为:审计与告警系统读到的手机号是 `138****1234`,按号码聚合日志的场景要意识到这一点。
- 回归锚点:`PhoneNumberMaskerTest`(打码语义与数字边界)、`StructuredLogMaskingTest`(encoder 级,message/stack_trace/控制组/MDC 直通)、`ObservabilityContractTest` 的两个打码用例(真实 application.yml 接线,CapturedOutput 断言)。
