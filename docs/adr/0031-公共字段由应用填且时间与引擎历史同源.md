# 公共字段由应用填且时间与引擎历史同源

`BaseEntity` 一直有 `create_time` / `update_time`，但没有任何写入者：DDL 是 `DEFAULT NULL`，
全仓库只有两处手工 `setCreateTime`。栈上实测 `oa_process` 41 行、`oa_process_record` 49 行、
`sys_user` 2 行的两列全为 NULL，配置页「创建时间」列因此整列为空，按时间范围筛选也筛不出数据。
决定：公共字段由 `CommonFieldsMetaObjectHandler` 在应用侧填写（插入填两列、更新刷新
`update_time`），数据库列只加 `DEFAULT (CURRENT_TIMESTAMP)` 作直接 SQL 的兜底；同时把
数据库会话时区钉成 `+08:00`。

理由：数据库时钟在这个栈上已经是另一套时间。compose 的 `mysql:8.4` 默认 UTC，而 JDBC URL
声明 `serverTimezone=GMT+8`——同一张 `oa_attachment` 里，`create_time` 由
`DEFAULT CURRENT_TIMESTAMP` 写成 UTC（06:06:56），`upload_expires_at` 由应用写成 GMT+8
（14:11:56），差 8 小时；`cleanupExpiredPending()` 用 `create_time <= now-24h` 判定，pending
附件会被提前约 8 小时清掉。业务时间必须与引擎 `ACT_HI_PROCINST.START_TIME_`、Jackson 输出
同源，所以由应用在动作发生时写入，不由库补。

历史 NULL 行只回填可证的部分：`oa_process.create_time` 用
`ACT_HI_PROCINST.START_TIME_`（41/41 可 join）。`oa_process_record`、`sys_user` 在引擎历史里
没有稳定对应关系，保持 NULL，不编造——与 V4「不可证的已发布模板不回填」同一立场。回填写成
Java 迁移（V104）而不是 SQL：空库首启动时 `ACT_*` 由 Flowable 在 Flyway 之后创建，直接写
`UPDATE ... ACT_HI_PROCINST ...` 会在这种库上因表不存在而失败。

## 考虑过的替代方案

- **只靠 DDL 默认值**（零 Java）：这正是 `oa_attachment` 今天的写法，也是上面 8 小时分叉的
  来源；业务时间会跟着数据库会话时区漂。
- **只靠 handler，DDL 保持 `DEFAULT NULL`**：任何绕过实体的直接 SQL（演示播种、人工修数）
  仍会留下空时间，而空时间正是这次的缺陷本身。
- **让 `oa_process_template_publication` 也继承 `BaseEntity`**：`BaseEntity` 带
  `@TableLogic is_deleted`，那张表刻意没有这个列（证据不应可删），继承会让每条查询带上
  `is_deleted=0` 直接报错。它写一次不复更，靠 V103 的默认值即可。

## 后果

- 已知边界：MyBatis-Plus 只在 `update(entity, wrapper)` 且 entity 非空时触发更新填充；
  `LambdaUpdateWrapper` 不传实体的更新（含逻辑删除）不会刷新 `update_time`。这是可接受的
  取舍——旧行为是"有的地方手写、有的地方完全不写"，比一个有明确边界的窟窿更难解释。
- 任何部署都必须保证数据库会话时区与应用一致（`sessionVariables=time_zone='+08:00'` 或
  服务端 `default-time-zone=+08:00`）。只改其中一处，兜底值仍会差一个时区。
- `SysUserController` 里为了"让 update 语句非空"而手写的 `setUpdateTime` 已删除：handler 会填，
  而且它填的理由是公共字段语义，不是为了让 SQL 有 SET 子句。
- 客户端「创建时间」列从此有值；`p0-3` 栈用例断言发起后 `createTime` 非空，
  `CommonFieldsFillContractTest` 锁住插入填充、更新刷新与逻辑删除三条行为。
