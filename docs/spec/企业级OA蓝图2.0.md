# 企业级 OA 蓝图 2.0

> 来源：地图 [#267](https://github.com/lautung/guigu-oa/issues/267) 的蓝图票 [#268](https://github.com/lautung/guigu-oa/issues/268)。事实输入：研究 [#269](https://github.com/lautung/guigu-oa/issues/269)（审批动作与 Flowable 8）、[#270](https://github.com/lautung/guigu-oa/issues/270)（人事/考勤/报销数据模型）。本文件是地图的终点产物与后续所有票的裁决基准；它只定决策，不写实现。

## 1. 定位、判据与边界

云尚办公从「平台基座 + 审批」升级成**小团队真跑（3–30 人）的企业级 OA**：日常在用是硬判据，面试展示是副产品。主线只有两条：

1. **审批深度**：转办、前/后加签、撤回、催办 + 动态审批人（部门负责人/角色/岗位）。
2. **OA 业务域**：人事档案、考勤、报销三个 P0 域；日程会议、文档知识库两个 P1 域。

每项新能力必须回答与审批的共存关系：**业务单据 → 审批 → 回写**（ADR 0066）。业务单据有自己的状态，审批实例只作过程真相。

不做（沿用地图 Out of scope 与章程决议）：

- 平台企业化：SSO/LDAP/OIDC、邮件/短信通道、IM、开放 API/Webhook、站内消息中心。
- 非功能：备份恢复、审计保留期、集群 HA、容量与 SLO。
- 多租户 SaaS、小程序/App、企业微信/钉钉深度集成。
- 资产、公文、通用合同管理（员工合同在人事域内）；招聘、绩效、薪酬；复杂排班、弹性工时、多地点打卡。
- 在线代码生成器、多数据源、Druid 控制台（ADR 0062 维持）。

## 2. 形态

- **一级六项**：工作台 / 办事 / 业务 / 系统管理 / 系统监控 / 系统工具。新增「业务」承载三个经营域；ADR 0051 的「五项固定」随之修订（ADR 0059 同）。
- **办事 = 登录即有的个人办事面**：审批五种列表 + 我的考勤（打卡、我的申请、考勤记录与假期）+ 我的报销（我的报销单）。不吃后台授权，手机完整可用。
- **业务 = 后台授予的管理面**：人事管理、考勤管理、报销管理。页面与按钮点照常走角色授予（ADR 0052/0056）。
- **两套发起入口**：业务单据走域内发起页（我的报销 → 新建报销单、我的考勤 → 新建请假/加班）；无专用单据的通用事项仍走「发起审批」的 form-create 模板。文案上明确区分「业务单据」与「通用审批」。
- **桌面优先、手机全面可用**不变（ADR 0051）：打卡与请假在窄屏同样可完成。

每波验收口径：合同测试（H2）+ API 端点套件 + 一条 e2e-stack 主路径（提交 → 审批 → 回写）；性能与安全只在波末按 ADR 0030 跑，日期与轮次见 `docs/agents/testing.md`。

首版边界：

- **人事**：不做招聘/绩效/薪酬；合同到期只做列表角标与统计卡，不新开通知出口（本仓通知口径只有待处理与公告）。
- **考勤**：不做外出/出差、排班、弹性工时、多地点；补卡由后台直接改记录（不走审批），写审计日志。
- **报销**：不做发票号去重、Excel 导出、预算、借款、对公付款、税务。

## 4. 权限与数据范围

- 三层（页面授予 / 按钮点 / 数据范围）与 gate 判定顺序不变（ADR 0052/0056）：页面先、按钮后，拒绝都是 HTTP 200 + code 205。
- 新域权限标识前缀：`hr:`、`attendance:`、`expense:`，形状仍是 `模块:对象:动作`（如 `hr:employee:edit`）。
- 新域页面路径一律绝对：`/business/hr/...`、`/business/attendance/...`、`/business/expense/...`；菜单与按钮点种子随各域票的迁移落库。
- 数据范围五档语义与多角色并集不变（ADR 0053/0057）；作用面扩展如下，每个查询自己回答部门列与本人列：

| 查询                       | 部门列                              | 本人列                       |
| -------------------------- | ----------------------------------- | ---------------------------- |
| 员工档案                   | `hr_employee.dept_id`               | `hr_employee.user_id`        |
| 员工异动                   | 异动发生时的部门快照                | `hr_employee_change.user_id` |
| 员工合同                   | `hr_employee.dept_id`（员工当前）   | `hr_employee.user_id`        |
| 调岗单 / 离职单            | 提交时员工部门快照                  | 员工账号快照                 |
| 打卡记录 / 补卡 / 假期发放 | `sys_user.dept_id`（当前）          | `sys_user.id`                |
| 月度考勤统计               | `sys_user.dept_id`（当前）          | `sys_user.id`                |
| 报销台账 / 统计            | `expense_claim.dept_id`（提交快照） | `expense_claim.applicant_id` |

- 办事个人面不套数据范围：构造上只读本人。
- 「财务」不是新的数据范围档，是角色 + 页面授予；「主管看本部门」由数据范围档表达。
- 部门集为空且不是 `unrestricted` 时仍是零行，不是全部；解析不缓存、不进 `/info`。

## 5. 数据模型原则

1. **账号与员工分离**：`sys_user` 只管登录与组织归属；人事档案是独立主数据，不往 `sys_user` 塞工号/合同/离职字段。员工可无账号（待入职/已离职），见 ADR 0071。
2. **单据态与审批态分离**：单据有自己的状态机（草稿/审批中/通过/拒绝/撤回）；审批实例只作过程真相；回写**单向**审批 → 单据，单据不反写审批。
3. **发起与回写同一事务边界**：沿用 ADR 0012 的持久化副本 + 回滚补偿；幂等键形状由关联票定。
4. **每域自己的单据表**：不做通用 JSON 单据表；业务单据用自己的 DTO 与 jsr303 校验（ADR 0033）。
5. **提交时快照**：单据落库时记下部门、申请人与金额类字段；列表与统计读快照，不随调岗漂移。
6. **引用 ID 不快照姓名**：主数据（员工/部门/岗位）的展示名走 join。
7. **业务 key 定在审批行**：`oa_process.business_type`/`business_id` + 普通联合索引（ADR 0067）；一单可多审批、同一时刻最多一条进行中；值域命名 `<域>.<单据>`（`hr.transfer`、`attendance.leave`、`expense.claim`）。

## 6. 目标菜单树

```text
工作台
办事
  发起审批 / 待处理 / 已处理 / 已发起 / 抄送我的
  我的考勤：打卡 / 我的申请（请假·加班）/ 考勤记录与假期
  我的报销：我的报销单
业务
  人事管理：员工档案 / 员工异动 / 合同
  考勤管理：考勤组与班次 / 打卡记录 / 补卡处理 / 假期类型与发放 / 月度统计
  报销管理：报销台账 / 统计
系统管理（不变）
系统监控（不变）
系统工具（不变）
```

个人中心仍在顶栏，路由 `/profile` 不进后台菜单。

## 8. 票与依赖

- **W1**：#271（审批深度）与 #272（关联形状）同波，互不阻塞；两者收口后 W2 才开。
- **W2**：#273（人事形状，ADR 0071）→ 实现票。
- **W3**：#274（考勤形状）→ 实现票。
- **W4**：#275（报销形状）→ 实现票。
- **W5**：P1 两域留在地图 fog，P0 稳定后按届时的最短路径拆票。

硬依赖：关联形状先于三个域的实现；动态审批人先于请假/调岗/报销单的模板配置（否则审批人只能写死用户名）。
