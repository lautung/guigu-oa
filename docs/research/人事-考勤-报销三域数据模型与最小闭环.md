# 人事、考勤、报销三域的数据模型与最小闭环

> 研究票：[研究：企业级人事/考勤/报销域的数据模型与最小闭环](https://github.com/lautung/guigu-oa/issues/270)  
> 地图票：[wayfinder 地图：升级成小团队真跑的企业级 OA（审批深度 + 人事/考勤/报销）](https://github.com/lautung/guigu-oa/issues/267)  
> 来源：本仓库 `server/lautung-oa-parent`；Odoo 18.0；Frappe HR / ERPNext（含 Employee Transfer / Promotion / Separation）；Dolibarr；芋道 `ruoyi-vue-pro`；飞书开放平台通讯录 API；MySQL 8.4 手册；国家税务总局公告 2018 年第 28 号。完整 URL 与行号见文末「来源」。  
> 说明：只报事实、模型与可复用面，不做产品选型、不写实现建议。文中的「最小集」指可观察到的实现公共字段交集，不是推荐方案。

## 结论

1. **账号与员工是两张不同的表。** 本仓 `sys_user` 只有登录名、密码、姓名、手机、头像、部门、账号状态等字段（`V1:7-23`），没有工号、证件、入职日期、试用期、合同、离职字段。三套实现都把员工档案独立出来：Odoo 的 `hr.employee.user_id` 是可空关联（`E1:39-47`），Frappe/ERPNext 的 `Employee.user_id` 只是 User 链接（`F1:286`），芋道 `hrm_employee.user_id` 明确「允许为空，用于待入职、离职历史等没有登录账号的员工档案」（`Y1:55-62`）。

2. **人事档案的四块在实现里是可分离的。** 芋道拆成员工主档、合同、异动、离职四组表（`Y1`、`Y2`、`Y3`、`Y4`）；Odoo 用 `hr.employee` 加多段 `hr.contract`，任职期间放在合同行上（`E1:50-143`、`E2:24-80`）；Frappe 用一张宽 `Employee` 加教育、外部工作、内部任职经历子表（`F1:211-378`、`F1:587-642`）。

3. **合同到期提醒需要三样东西：结束日期、提醒窗口、调度/通知。** Odoo 在公司设置里读 `contract_expiration_notice_period`，扫描 `state=open` 且 `date_end` 落在窗口内的合同，并在合同结束日建待办活动（`E2:168-180`）；Frappe 在 Employee 上有 `contract_end_date` 与 `notice_number_of_days`（字段标签是 Notice (days)，是通知期，不是到期提醒窗口；`F1:335-342`），本次读取的 Employee JSON 与 `employee.py` 没有到期扫描任务；芋道合同有 `expireRemind` 标记（`Y2:92`），合同 mapper 有按 `expireRemind=true` + `status=进行中` + `endTime` 区间统计的查询（`Y-contract:29-41`），但本次读取的 `job/employee` 目录只有异动任务，没有合同到期扫描 Job（见来源 `Y-job`）。

4. **固定班模型的最小形状是「考勤组 + 班次 + 工作日 + 打卡窗口 + 休息段 + 特殊日期」。** 芋道 `hrm_attendance_group` 的 `shifts` JSON 明确给出 `weeks`、`startTime`、`endTime`、`clockInStartTime`、`clockInEndTime`、`clockOutStartTime`、`clockOutEndTime`、`restStartTime`、`restEndTime`、`excludeRestTime`（`Y5:79-186`）；Frappe 用 `Shift Type` 加 `Shift Assignment`（`F5`）；Odoo 用 `resource.calendar` 的 `attendance_ids`（`dayofweek`、`hour_from`、`hour_to`）和员工上的 `resource_calendar_id`（`E4:88-109`、`E1:50`）。

5. **打卡记录是独立事件表，补卡/外出在实现里另有入口。** 芋道 `hrm_attendance_clock` 记录 `clockTime`、`type`、`attendanceTime`、`sourceType`、`status`、地理位置和 WiFi（`Y6:42-107`），来源只有「手机端/手工录入」（`Y11:19-20`），没有独立补卡审批单；Frappe 用 `Employee Checkin` 的 IN/OUT 事件加 `Attendance Request`（原因只有 Work From Home / On Duty），`Attendance Request` 提交时创建或改写 `Attendance`（`F3:37-74`、`F4:216-260`）；Odoo `hr.attendance` 只有 `check_in`/`check_out`、`in_mode`/`out_mode`（kiosk、systray、manual、technical），没有班次外键（`E3:42-78`）。

6. **假期余额需要「类型 + 发放 + 流水」。** Odoo 有 `hr.leave.type`（`requires_allocation`、`allows_negative`、`request_unit` 等）、`hr.leave.allocation`（`date_from/to`、`number_of_days`、`allocation_type`、`accrual_plan_id`、`max_leaves`、`leaves_taken`、结转过期字段）与 `hr.leave`（`state`、`date_from/to`、`number_of_days`）；余额还区分 `remaining_leaves`、`virtual_remaining_leaves`、`leaves_requested`、`leaves_approved`、`leaves_taken`（`E6:55-127`、`E7:70-117`、`E7:485-525`）。Frappe 有 `Leave Type`、`Leave Allocation`、`Leave Application`、`Leave Ledger Entry`，发放为正、请假为负、结转带 `is_carry_forward`、过期带 `is_expired`（`F6`、`F7`、`F8:702-731`、`F9:90-115`）。芋道 `hrm_attendance_leave` 只有类型、起止、天数、审批状态和流程实例，没有余额/发放/流水实体（`Y7:39-91`）。

7. **审批通过后的考勤写入有三种事实路径。** Frappe 的 `Leave Application` 在 `status == Approved` 时逐日创建或更新 `Attendance`，状态置 `On Leave` 或 `Half Day` 并回填 `leave_application`（`F8:300-364`）；Odoo 在请假验证时写 `resource.calendar.leaves`，不改 `hr.attendance`（`E5:909-926`）；芋道只由监听器回写请假记录的 `approvalStatus`/`approvalTime`/`approvalReason`，统计时只读 `APPROVE` 的请假并按分钟扣减，不创建打卡行（`Y10:27-31`、`Y9:363-430`）。

8. **报销最小模型是「单头 + 明细 + 票据附件 + 审批状态/流程实例」。** 芋道 `oa_reimbursement` 的字段是标题、紧急程度、原因、证明人、客户名、报销方式、票据总数、总金额、审批状态、流程实例、`items` JSON、`fileUrls` JSON；明细只有费用时间、费用类型、说明、票据张数、金额（`Y13:39-136`）。Frappe 用 `Expense Claim` 加 `Expense Claim Detail` 子表，另有 `total_claimed_amount`、`total_sanctioned_amount`、`is_paid`、`total_amount_reimbursed`、`clearance_date`、币种/汇率（`F11`）。Odoo 用 `hr.expense` 行加 `hr.expense.sheet` 单头，含税额、公司币种金额、`payment_state`、`account_move_ids`（`E8:26-208`、`E9:55-212`）。

9. **金额精度与币种在实现里分成三档。** Odoo 用 `fields.Monetary` + `currency_id`/`company_currency_id`/`currency_rate`，币种精度由 `res.currency.rounding` 推出 `decimal_places`（`E8:114-166`、`E10:39-41`、`E10:165-170`）；Frappe 用 `Currency` 字段、`currency`/`exchange_rate` 和 `base_*` 公司币种金额，币种表有 `smallest_currency_fraction_value`（`F11:410-422`、`F13`）；芋道用 Java `BigDecimal` 且注释「单位：元」，没有币种字段（`Y13:76-87`）；Dolibarr 的金额列是 `double(24,8)` 并另存 `multicurrency_*` 列（`D1:25-63`、`D2:30-54`）。MySQL 手册明确 `DECIMAL` 是精确值、`FLOAT`/`DOUBLE` 是近似值（`M1`、`M2`）。

10. **可复用面集中在平台层，业务表必须新增。** 账号、组织树、岗位标签、角色数据范围、审批账本与动作记录、审批模板与发布证据、私有对象存储、定时任务、字典/参数、后台审计都可直接复用（见第 5 节）。但 `sys_user` 不能当员工档案；`oa_attachment` 只绑 `process_id`/`draft_id`，没有 `employee_id`/`contract_id`/`invoice_id`，没有 checksum，草稿态 24 小时后会被清理；`sys_dept.leader` 是 `VARCHAR(50)` 姓名，不是用户外键；`sys_post` 只是职务标签，不产生授权；`oa_process.form_values` 是 `TEXT`，不能当台账列。

11. **审批接缝的关键事实是 businessKey。** 本仓 `ApprovalWriter` 把 `String.valueOf(process.getId())` 传给引擎（`R14:107-110`），即 Flowable 的 businessKey 指向 `oa_process.id`，不是未来人事/考勤/报销业务表的 id。业务表若存 `process_id` 指向 `oa_process`，与这个 businessKey 一致；若业务表想用自身 id 当 businessKey，需要改发起路径。芋道的做法相反：业务表存 `processInstanceId`，`businessKey` 直接用业务记录 id（`Y10:87-93`、`Y13:83-86`）。

12. **不做预算、借款、对公付款时，模型可以缩到审批单。** 芋道 `oa_reimbursement` 没有预算、借款、支付状态/时间、会计凭证字段，只有审批状态（`Y13`）；`oa_travel_reimbursement` 多一个 `payStatus`（`Y14:78-82`）。Frappe 把这些作为独立能力：`Employee Advance` / `advances` 子表、`total_advance_amount`、`is_paid`、`clearance_date`、`total_amount_reimbursed`（`F11:159-319`）；Odoo 用 `payment_mode`、`payment_state`、`account_move_ids`（`E8:170-180`、`E9:167-211`）；Dolibarr 的状态含 6=paid 并有 `fk_bank_account`（`D1:46-63`）。省略这些能力时，对应的表和字段可以整块不存在。

## 2. 人事档案

### 2.1 员工档案字段集

三套实现的总形状不同，但字段可以按「基础身份 / 任职 / 合同 / 离职」四块对齐。

| 维度 | Odoo 18 `hr.employee` + `hr.contract` | Frappe/ERPNext `Employee` | 芋道 `hrm_employee` + 合同/异动/离职 |
|---|---|---|---|
| 主键与账号 | `hr.employee.id`；`user_id` 关联 `res.users`，可空；`active` 控制在职/归档（`E1:39-49`） | `employee` 主键；`user_id` 关联 User；`status` 为 Active/Inactive/Suspended/Left（`F1:211`、`F1:286`） | `hrm_employee.id`；`userId` 关联后台用户，**允许为空**，用于待入职/离职历史（`Y1:55-62`） |
| 基础身份 | `name`、`gender`、`marital`、`birthday`、`place_of_birth`、`country_of_birth`、`identification_id`、`passport_id`、`ssnid`/`sinid`、`private_phone`/`private_email`、`private_street`/`private_city`/`private_zip`/`private_country_id`、`emergency_contact`/`emergency_phone`、`study_field`/`study_school`、`certificate`（`E1:56-125`） | `first_name`/`middle_name`/`last_name`/`employee_name`、`employee_number`、`gender`、`date_of_birth`、`cell_number`、`company_email`/`personal_email`、`permanent_address`/`current_address`、`passport_number`、`marital_status`、`blood_group`、`education` 子表、`external_work_history` 子表（`F1:221-378`、`F1:587-603`） | `name`、`jobNumber`、`mobile`、`country`、`nation`、`idType`/`idNumber`、`sex`、`email`、`nativePlace`、`birthday`、`age`、`address`、`highestEducation`（`Y1:49-122`） |
| 任职 | `department_id`、`job_id`、`parent_id`（直属上级，`child_ids` 反向）、`resource_calendar_id`、`employee_type`、`barcode`/`pin`（`E1:50-146`）；任职期间还落在 `hr.contract` 的 `department_id`/`job_id`（`E2:29-32`） | `department`、`designation`、`reports_to`、`date_of_joining`、`final_confirmation_date`、`notice_number_of_days`、`holiday_list`、`branch`（`F1:324-378`） | `deptId`、`leaderEmployeeId`、`entryStatus`、`status`、`type`、`entryTime`、`probation`（月）、`regularTime`、`postName`、`postLevel`、`workCity`/`workAddress`/`workDetailAddress`、`companyAgeStartTime`/`companyAge`（`Y1:122-201`） |
| 合同 | 独立 `hr.contract`：`name`、`employee_id`、`date_start`、`date_end`、`trial_date_end`、`wage`、`state`、`contract_type_id`、`resource_calendar_id`、`department_id`、`job_id`（`E2:24-80`） | 合同信息在 Employee 宽表：`contract_end_date`、`notice_number_of_days`；没有独立合同主表（`F1:335-342`） | 独立 `hrm_employee_contract`：`employeeId`、`no`、`type`、`startTime`、`endTime`、`term`（年）、`status`、`signCompany`、`signTime`、`remark`、`expireRemind`、`fileUrls`（`Y2:47-101`） |
| 离职 | `departure_reason_id`、`departure_description`、`departure_date`（`E1:148-151`） | Employee 宽表有 `resignation_letter_date`、`relieving_date`、`reason_for_leaving`、`leave_encashed`、`encashment_date`、`exit_interview_details`（`F1:626-642`）；另有独立 `Employee Separation` 单据，含 `resignation_letter_date`、`boarding_begins_on`、`boarding_status`、`activities` 子表、`exit_interview`（`F17`） | `leaveTime` 在主档（`Y1:167`）；独立 `hrm_employee_quit_info`：`planQuitTime`、`applyQuitTime`、`salarySettlementTime`、`type`、`reason`、`remark`、`oldEmployeeStatus`（`Y3:45-79`） |
| 异动 | 多段 `hr.contract` 用 `date_start`/`date_end` 表达任职期间；`hr.employee.department_id`/`job_id` 是当前值（`E2:29-37`） | `internal_work_history` 子表保存部门/职务/分支的 `from_date`/`to_date`（`F1:613`、`F14`）；独立 `Employee Transfer` 单据有 `transfer_date`、`transfer_details` 子表、`new_company`/`create_new_employee_id`，提交时用 `update_employee_work_history` 写回 Employee（`F15`）；`Employee Promotion` 单据有 `promotion_date`、`promotion_details`、`current_ctc`/`revised_ctc`（`F16`） | `hrm_employee_change_record`：`type`、`reason`、`oldDeptId`/`newDeptId`、`oldPostName`/`newPostName`、`oldPostLevel`/`newPostLevel`、`oldWorkAddress`/`newWorkAddress`、`oldLeaderEmployeeId`/`newLeaderEmployeeId`、`probation`、`effectTime`、`appliedTime`、`remark`（`Y4:45-121`） |

事实含义：

- Odoo 的「入职日期」不在 `hr.employee` 的字段清单里，而在 `hr.contract.date_start`；一个员工可以有多段合同，任职期间由合同行表达（`E1:39-159`、`E2:33-37`）。这让「合同」和「任职」共用一张表，历史任职天然按合同分段。
- Frappe 把合同结束日、试用转正日、离职日都放在 Employee 宽表上（`F1:324-342`、`F1:626-642`），没有独立合同行；员工换合同只改宽表字段，不保留多段合同历史，历史任职由 `internal_work_history` 子表补足。调岗/晋升另有 `Employee Transfer`/`Employee Promotion` 单据，提交时把 `transfer_details`/`promotion_details` 的 `fieldname`/`current`/`new` 行写回 Employee 并追加到任职历史（`F15`、`F16`）。
- 芋道把「员工主档 / 合同 / 异动 / 离职」拆成四张表，异动记录显式保存旧值和新值，离职记录单独保存计划离职、申请离职、薪资结算时间（`Y1`、`Y2`、`Y3`、`Y4`）。Frappe 的异动明细是「字段名 + 当前值 + 新值」的通用行（`F15` 的 `transfer_details`），芋道是固定的 `old*`/`new*` 列；两者都把差异保存在独立记录里，形状不同。

### 2.2 与账号（`sys_user`）的边界

本仓 `sys_user` 的实际列是 `id`、`username`、`password`、`name`、`phone`、`head_url`、`dept_id`、`post_id`、`description`、`open_id`、`status`、`create_time`、`update_time`、`is_deleted`（`V1:7-23`），后来增加了 `token_version`（`V102`）和用户名唯一索引（`V106`）；`post_id` 已被 V110 回填到 `sys_user_post` 并删除（`R6:98-113`）。实体上没有工号、证件、生日、性别、入职日期、试用期、合同、离职字段（`R8:19-86`）。

`sys_user.status` 的注释是「1：正常 0：停用」（`R8:57-59`），它是**账号状态**，不是任职状态。`is_deleted` 是 MyBatis-Plus 的逻辑删除（`R8` 继承 `BaseEntity`，`BaseEntity` 的 `@TableLogic`），软删行对查询不可见但仍占唯一索引（`V106` 的注释明确说明这一点）。因此：

- 待入职员工可以没有账号；离职员工的历史档案不能依赖 `sys_user` 行继续可见。芋道把 `userId` 设计成可空，并在注释里直接写明「用于待入职、离职历史等没有登录账号的员工档案」（`Y1:55-62`）。
- Odoo 的 `hr.employee.user_id` 是 `Many2one('res.users')`，`ondelete='restrict'`，但员工本身有 `active` 和 `departure_date`（`E1:39-49`、`E1:148-151`）；Frappe 的 `Employee.user_id` 只是链接，`Employee.status` 可以是 `Left`（`F1:211`、`F1:286`）。两套实现都不把「删除账号」当成「删除员工」。
- 本仓种子账号 `admin`/`user` 没有员工档案（`V1:162-168`）；反过来，员工档案也不应要求每个员工都有登录账号。账号与员工是可选的一对一，不是同一张表。

### 2.3 入职、离职、调岗记录

| 记录 | Odoo 18 | Frappe/ERPNext | 芋道 |
|---|---|---|---|
| 入职 | `hr.contract.date_start`、`trial_date_end`；员工 `departure_date` 为空表示在职（`E2:33-37`、`E1:148-151`） | `date_of_joining`、`final_confirmation_date`、`scheduled_confirmation_date`（`F1:246`、`F1:324`） | 主档 `entryTime`、`probation`、`regularTime`、`entryStatus`（`Y1:135-166`） |
| 离职 | `departure_reason_id`、`departure_description`、`departure_date`；合同 `state` 可置 `close`（`E1:148-151`、`E2:45-51`） | Employee 宽表有 `resignation_letter_date`、`relieving_date`、`reason_for_leaving`、`leave_encashed`、`encashment_date`（`F1:626-642`）；另有 `Employee Separation` 单据保存离职流程、活动清单与离职面谈（`F17`） | `leaveTime` + `hrm_employee_quit_info` 的 `planQuitTime`/`applyQuitTime`/`salarySettlementTime`/`type`/`reason`/`oldEmployeeStatus`（`Y1:167`、`Y3:45-79`） |
| 调岗 | 新合同行或改 `hr.employee.department_id`/`job_id`；没有独立的 old/new 异动表（`E2:29-37`） | `internal_work_history` 子表按 `from_date`/`to_date` 保存部门/职务/分支（`F1:613`、`F14`）；`Employee Transfer`/`Employee Promotion` 单据保存 `transfer_date`/`promotion_date` 与变更明细，提交时写回 Employee（`F15`、`F16`） | `hrm_employee_change_record` 显式保存 old/new 部门、职务、职级、工作地址、直属上级，以及 `effectTime`/`appliedTime`（`Y4:45-121`） |

本仓没有员工异动/离职表；`sys_oper_log` 是后台写操作审计（`docs/agents/server-modules.md:44`），`oa_process_record` 是审批动作账本（`V1:145-156`、`docs/agents/server-modules.md:44`），都不记录「旧部门 → 新部门」这种人事事实。人事域要回答「谁在什么时候从哪个部门调到哪个部门」，必须新增业务历史表或把异动做成审批业务单。

### 2.4 合同与到期提醒

三套实现的合同字段与提醒能力：

- Odoo `hr.contract`：`name`、`employee_id`、`date_start`、`date_end`、`trial_date_end`、`wage`、`state`（draft/open/close/cancel）、`contract_type_id`、`department_id`、`job_id`、`resource_calendar_id`（`E2:24-80`）。到期提醒不是合同表上的布尔开关，而是 `update_state()` 里按公司配置扫描：`state='open'`、`date_end <= today + contract_expiration_notice_period`、`date_end >= today + 1`，然后在 `date_end` 建活动（`E2:168-180`）。
- Frappe `Employee`：`contract_end_date`、`notice_number_of_days`（字段标签是 Notice (days)，是通知期，不是到期提醒开关；`F1:335-342`）；本次读取的 Employee JSON 与 `employee.py` 中没有到期提醒任务/窗口字段，只有合同结束日期可被外部调度器扫描。
- 芋道 `hrm_employee_contract`：`startTime`、`endTime`、`term`、`status`、`expireRemind`、`fileUrls`（`Y2:61-101`）。`expireRemind` 是布尔标记，合同 mapper 按 `expireRemind=true`、`status=进行中`、`endTime` 落在区间内统计人数（`Y-contract:29-41`），该计数被 HRM 首页 `TodoSurvey.toExpireContractCount` 使用（`Y-contract-home:418-424`）；本次读取的 `job/employee` 目录下只有 `HrmEmployeeChangeJob`，没有合同到期扫描 Job（`Y-job`）。

因此「合同到期提醒」的最小事实输入是：合同结束日期、提醒提前天数、一个按日/按周运行的调度器、一个提醒出口。本仓已有 `sys_job` 表与 `MonitorJob` 注册接口（`V120:3-42`、`R23:3-18`），可以承载调度；本仓没有按用户的消息/通知表，`notice` 是公告三态（`docs/agents/server-modules.md:20`），不是个人提醒。合同到期提醒若只做「列表筛选/导出」不需要新通知表；若要做「提前 N 天提醒本人/HR」，必须新增通知出口。

### 2.5 人事档案的可观察最小公共字段集

把三套实现取交集，员工主档至少需要：

- 员工标识：内部 id、工号/员工编号、姓名。
- 基础身份：性别、出生日期、证件类型/号码、手机、邮箱、地址、紧急联系人、学历。
- 任职：部门、职务/岗位、直属上级（员工维度）、入职日期、聘用形式、试用期、转正日期、工作地点、在职状态。
- 合同：合同编号、合同类型、开始/结束日期、试用期结束日、签约公司、签订日期、合同状态、合同附件、到期提醒标记/窗口。
- 离职：离职日期、离职类型/原因、计划/申请/薪资结算日期、离职前状态。
- 异动：异动类型/原因、旧/新部门、旧/新职务、旧/新职级、旧/新工作地点、旧/新直属上级、生效时间、申请时间。

这些字段在 `sys_user` 中都不存在（`V1:7-23`、`R8`），在企业微信/飞书通讯录的账号对象里也只覆盖一部分：飞书创建成员 API 接受 `name`、`mobile`、`department_ids`、`employee_type`、`email`、`employee_no`、`job_title`、`leader_user_id`、`gender`、`avatar_key`，并明确这是 contact user/account，不是 HR employee record（`G1`）。这佐证了「通讯录账号」与「人事档案」是两个对象。

## 3. 考勤

### 3.1 固定班模型

三套实现的班次表达：

| 要素 | 芋道 HRM | Frappe HR | Odoo 18 |
|---|---|---|---|
| 适用人 | `hrm_attendance_group.deptIds`、`employeeIds`、`defaultStatus`（`Y5:59-107`） | `Shift Assignment` 按 `employee` + `start_date`/`end_date` + `status` 分配（`F5`） | `hr.employee.resource_calendar_id` 指向一个工作日历（`E1:50`） |
| 工作日 | `Shift.weeks` 数组（`Y5:142-146`） | `Shift Type` 本身不含星期；由 `Shift Assignment` 的日期范围与 `Holiday List` 决定（`F5`） | `resource.calendar.attendance_ids` 的 `dayofweek`/`hour_from`/`hour_to`（`E4:63-78`、`E4:88-90`） |
| 上下班时间 | `Shift.startTime`、`endTime`（`Y5:147-155`） | `Shift Type.start_time`、`end_time`（`F5:42-49`） | `resource.calendar.attendance_ids` 的 `hour_from`/`hour_to`（`E4:88-90`） |
| 打卡窗口 | `clockInStartTime`/`clockInEndTime`、`clockOutStartTime`/`clockOutEndTime`（`Y5:157-175`） | `begin_check_in_before_shift_start_time`、`allow_check_out_after_shift_end_time`、`late_entry_grace_period`、`early_exit_grace_period`（`F5:102-120`） | `hr.attendance.check_in`/`check_out` 直接记录；没有独立打卡窗口字段（`E3:42-44`） |
| 休息段 | `restStartTime`/`restEndTime`、`excludeRestTime`（`Y5:177-186`） | `Shift Type.working_hours_threshold_for_half_day`、`working_hours_threshold_for_absent` 等（`F5:81-96`） | `resource.calendar.attendance_ids` 可有多段（含 lunch 段），`hours_per_day` 汇总（`E4:63-78`、`E4:98`） |
| 特殊日期 | `specialDates`（`type` + `date`）与 `rest`（法定节假日休息）（`Y5:83-127`） | `Holiday List` 挂在 `Shift Type`/`Employee` 上（`F2`、`F5`） | `resource.calendar` 的 `attendance_ids` 按周重复；公共假期由 `resource.calendar.leaves` 表达（`E5:909-926`） |
| 打卡地点 | `points`（经纬度/半径）、`wifis`（SSID/MAC）、`openWifiCard`/`openPointCard`（`Y5:70-107`、`Y5:196-240`） | `Employee Checkin` 有 `latitude`/`longitude`/`device_id`；地点规则不在本次读取的 Shift Type JSON 中（`F3:37-74`） | `hr.attendance` 记录 `in_latitude`/`in_longitude`/`in_ip_address`/`in_browser` 与 out 对应字段（`E3:52-77`） |
| 扣款规则 | `deductRule`（迟到/早退/旷工/缺卡的方式与金额）（`Y5:246-287`） | 不在 Shift Type JSON；由薪资/扣款规则另行实现（本次未覆盖） | 不在 `hr.attendance`；由薪资模块另行实现（本次未覆盖） |

事实结论：

- 「固定班」最小可运行形状是：一个考勤组/班次记录，含工作日集合、上班时间、下班时间、上班打卡窗口、下班打卡窗口、休息段、是否扣除休息；如果要做节假日，再加特殊日期/节假日表。芋道把这一整组放进 `hrm_attendance_group.shifts` 的 JSON（`Y5:79-186`），Frappe 用 `Shift Type` + `Shift Assignment` 两张表（`F5`），Odoo 用 `resource.calendar` + `resource.calendar.attendance`（`E4`）。
- 按人按日期排班不是固定班的最小必需项：芋道考勤组按部门/员工列表整体适用，`Shift.weeks` 固定到星期（`Y5:59-79`、`Y5:142-146`）；Frappe 才有 `Shift Assignment` 的 `start_date`/`end_date`（`F5`）。小团队固定班只需要「组 → 人」的归属，不需要逐日排班。
- Odoo 的 `hr.attendance` 没有班次外键；它通过员工的 `resource_calendar_id` 参与工作时段/加班计算，`expected_hours` 是 `worked_hours - overtime_hours`，不是独立的排班应出勤列（`E1:50`、`E3:78-83`）。因此「打卡记录」与「班次定义」在 Odoo 是两张表、通过员工关联，而不是打卡行上带 `shift_id`。

### 3.2 打卡与补卡

| 实现 | 打卡事件 | 打卡类型/来源 | 补卡/更正 |
|---|---|---|---|
| 芋道 HRM | `hrm_attendance_clock`：`employeeId`、`clockTime`、`type`、`attendanceTime`、`sourceType`、`status`、`stage`、`address`、`longitude`/`latitude`、`ssid`/`mac`、`remark`（`Y6:42-107`） | `type`：上班/下班（`Y11:19-20`）；`sourceType`：手机端/手工录入（`Y11:19-20`）；`status`：正常/迟到/早退/缺卡（`Y11:19-22`）；`stage`：第一段等（`Y11:19`） | 没有独立补卡审批实体；管理员可以更新/删除考勤记录（`Y-controller`），但这不是带审批的补卡单 |
| Frappe HR | `Employee Checkin`：`employee`、`log_type`（IN/OUT）、`time`、`device_id`、`shift`、`attendance`、`latitude`/`longitude`、`offshift`（`F3:37-74`） | `log_type` IN/OUT（`F3:54`） | `Attendance Request`：`employee`、`from_date`/`to_date`、`half_day`、`reason`（Work From Home / On Duty）、`explanation`、`shift`、`include_holidays`（`F4:31-134`）；提交时按日创建或更新 `Attendance`（`F4:216-260`） |
| Odoo 18 | `hr.attendance`：`employee_id`、`check_in`、`check_out`、`worked_hours`、`expected_hours`、`overtime_hours`、`in_latitude`/`in_longitude`/`in_ip_address`/`in_browser`、`in_mode`/`out_mode`（`E3:36-78`） | `in_mode`/`out_mode`：kiosk、systray、manual、technical；`out_mode` 另有 `auto_check_out`（`E3:58-77`） | 没有独立补卡单；手工改 `check_in`/`check_out`，`manual` 是打卡方式之一（`E3:58-77`、`E3:582-585`） |

事实结论：

- 「打卡」是事件表，字段至少包含员工、时间、类型（上班/下班）、来源（手机/手工/设备）、状态（正常/迟到/早退/缺卡）、地点/设备证据。芋道和 Frappe 都按这个形状建表（`Y6`、`F3`）；Odoo 把一次打卡收成 `check_in`/`check_out` 两列，不保留每一次原始事件（`E3:42-44`）。
- 「补卡」在实现里不是打卡事件的 `type`，而是一张申请单：Frappe 的 `Attendance Request` 带起止日期、半天、原因、说明，提交后写 `Attendance`（`F4`）；芋道没有补卡审批单，只有管理员直接改考勤记录（`Y-controller`）。如果业务要求「员工申请补卡 → 主管审批 → 改考勤」，必须新增补卡申请实体或复用审批模板 + 考勤写入。
- 「外出」在 Frappe 对应 `Attendance Request.reason = On Duty`（`F4:99`），在芋道 OA 的考勤类型里只有 `TRAVEL(4, 出差)`，没有单独的「外出」枚举（`Y12` 的 `OaAttendanceTypeEnum:18-21`）。「出差」在芋道是独立的 `oa_travel_apply` 单（`Y15`），在 Frappe 是独立的 `Travel Request` doctype（`F12`）。

### 3.3 假期类型与余额

#### 3.3.1 类型

- Odoo `hr.leave.type` 的配置字段包括：`name`、`leave_validation_type`、`requires_allocation`（no/yes）、`allocation_validation_type`、`request_unit`（hour/half_day/day）、`unpaid`、`include_public_holidays_in_duration`、`support_document`、`allows_negative`/`max_allowed_negative`、`max_leaves`、`leaves_taken`、`virtual_remaining_leaves`（`E7:32-117`）。
- Frappe `Leave Type` 的配置字段包括：`leave_type_name`、`max_leaves_allowed`、`applicable_after`、`max_continuous_days_allowed`、`is_carry_forward`、`is_lwp`、`is_optional_leave`、`allow_negative`、`include_holiday`、`is_compensatory`、`expire_carry_forwarded_leaves_after_days`、`allow_encashment`、`is_earned_leave`/`earned_leave_frequency`/`rounding`、`maximum_carry_forwarded_leaves`、`allow_over_allocation`（`F6:58-179`）。
- 芋道 `hrm_attendance_leave.type` 是 `String`，注释指向字典 `HRM_ATTENDANCE_LEAVE_TYPE`（`Y7:51-55`）；没有独立的假期类型表，也没有发放/余额实体。

事实结论：假期类型在 Odoo/Frappe 是数据表，在芋道是字典值。三套实现都没有把「年假 5/10/15 天」这类法定规则硬编码在核心模型里；类型、额度、是否带薪、是否允许负数、是否结转、结转有效期都是配置字段。

#### 3.3.2 发放、扣减、结转、冻结

| 动作 | Odoo 18 | Frappe HR | 芋道 HRM |
|---|---|---|---|
| 发放 | `hr.leave.allocation`：`date_from`/`date_to`、`number_of_days`、`allocation_type`（regular/accrual）、`accrual_plan_id`、`validation_type`（`E6:64-99`） | `Leave Allocation`：`from_date`/`to_date`、`new_leaves_allocated`、`total_leaves_allocated`、`unused_leaves`、`carry_forward`、`expired`（`F7:52-191`）；写 `Leave Ledger Entry` 时 `leaves = new_leaves_allocated`，`is_carry_forward=0`（`F8:702-731` 对应的 allocation 逻辑在 `F-allocation-py:336-360`） | 无发放实体 |
| 扣减 | `hr.leave` 的 `date_from`/`date_to`、`number_of_days`/`number_of_hours`、`state`（`E5:122-175`）；余额按 `remaining_leaves`/`leaves_taken` 汇总（`E7:485-525`） | `Leave Application.total_leave_days`（`F8:144`）与只读快照 `leave_balance`（申请前余额，`F8:105-110`）；写 `Leave Ledger Entry` 时 `leaves = total_leave_days * -1`（`F8:702-731`） | `hrm_attendance_leave.day`（`Y7:63`），只存时长，不扣余额 |
| 结转 | `hr.leave.allocation` 的 `expiring_carryover_days`、`carried_over_days_expiration_date`；`accrual_plan` 的 `carryover_date`/`carryover_month`/`carryover_day`（`E6:126-127`、`E6:299-314`） | `Leave Type.is_carry_forward`、`maximum_carry_forwarded_leaves`、`expire_carry_forwarded_leaves_after_days`（`F6:85-179`）；allocation 写 `unused_leaves` 且 `is_carry_forward=1`（`F-allocation-py:336-360`） | 无结转 |
| 过期/核销 | `expiring_carryover_days` + `carried_over_days_expiration_date`（`E6:126-127`） | 过期写负流水并标 `is_expired=1`（`F9:90-96`、`F9:248-285`） | 无过期 |
| 冻结/占用 | `virtual_remaining_leaves` 在请假申请时减少，`leaves_requested` 记录未批准的占用，`remaining_leaves` 只在批准后减少（`E7:514-521`） | 请假未批准不写流水（`F8:702-703`），因此没有单独的冻结行；批准后才写负流水 | 无余额，审批状态只是 `approvalStatus`（`Y7:77`） |

事实结论：

- 有余额的实现至少需要三张表/三层：类型（规则）、发放（额度与有效期）、流水（每次增加/扣减/结转/过期）。Odoo 把「发放」和「流水」合成 allocation + leave 计算；Frappe 把「流水」显式建成 `Leave Ledger Entry`，并用 `transaction_type`/`transaction_name` 指向来源单据（`F9:58-73`）。
- 「冻结」在 Odoo 的语义是 `virtual_remaining_leaves` 与 `leaves_requested`：申请一提交，虚拟余额减少，但 `leaves_taken`/`remaining_leaves` 只在批准后变化（`E7:514-521`）。Frappe 没有冻结行，未批准的 Leave Application 不写 ledger（`F8:702-703`）。
- 芋道的 `hrm_attendance_leave` 没有 `balance`/`remaining`/`allocation`/`ledger` 字段（`Y7:39-91`），`dal/dataobject/attendance/record` 目录也只有 clock 与 leave 两个实体（`Y-dir`）。因此「小团队最小集」如果不做假期余额，芋道的形状是可观察到的下限；如果要做余额，必须新增类型/发放/流水，不能只靠 leave 记录上的 `day`。

| 出差 | `hr.attendance` 没有出差字段；核心 `hr`/`hr_holidays` 本次未读到出差单模型 | `Travel Request` + `Travel Itinerary` 独立单，含 `travel_type`、`travel_funding`、`travel_proof`、`purpose_of_travel`、`itinerary` 子表、`costings` 子表（`F12`） | `oa_travel_apply` 单（`no`、`deptId`、`reason`、`startTime`/`endTime`、`days`、`companion`、`estimatedPrice`、`reimburseStatus`、`status`、`processInstanceId`、`items`、`fileUrls`）（`Y15`）；另有 `oa_travel_reimbursement` 单（`Y14`） |

事实结论：

- 审批通过后的考勤写入有两条路径：**写考勤行**（Frappe 的 `Attendance` On Leave/Half Day；`Attendance Request` 的 On Duty/WFH）与**保留申请记录、统计时读取**（芋道的 leave + `approvalStatus`）。Odoo 的请假写的是日历占用 `resource.calendar.leaves`，不是考勤行。
- 如果选择「写考勤行」，必须定义覆盖规则：已有正常打卡行是改状态还是另建行、半天怎么表示、撤销/拒绝时怎么回滚。Frappe 在 `create_or_update_attendance` 里处理了「Absent → On Leave」「Half Day」以及取消时删除/取消 Attendance（`F8:333-368`）。如果选择「统计时读取」，考勤行保持原始打卡，统计查询要按审批状态过滤，芋道的 `getEffectiveAttendanceLeaveList...` 就是只取 `APPROVE`（`Y10:162-173`）。
- 加班和出差在芋道是独立审批单，没有写 HRM 考勤表；Odoo 把加班挂在 `hr.attendance` 行上；Frappe 把加班字段挂在 `Attendance` 上。三种事实模型不同，决策票需要明确「加班是否产生调休余额」；本次读取的 Yudao 加班单没有调休/余额字段（`Y15`），Odoo 的 `hr.attendance.overtime` 只有日期、时长、调整标记（`E11:8-26`）。

### 3.5 统计口径

#### 芋道 HRM 的日结果与月报

日结果由 `calculateAttendanceDay` 计算（`Y9:347-430`），事实步骤是：

1. 取班次当天的起止时间，扣除 `Shift.restStartTime`/`restEndTime` 得到实际工作区间 `workRanges`，并算出 `scheduledMinutes`（`Y9:355-365`）。
2. 把有效请假记录与工作区间求交，得到 `leaveWorkRanges`/`leaveMinutes`，再按 `leaveMinutes / scheduledMinutes` 折算 `leaveDays`（`Y9:366-374`）。
3. 匹配上班/下班有效打卡；迟到/早退分钟数要扣除休息与请假覆盖区间（`Y9:376-425`）。
4. 下班打卡窗口结束后仍无任何打卡且存在未请假时长，计旷工；对应打卡窗口结束仍无打卡且未请假，计缺卡（`Y9:381-400`）。
5. 日结果枚举包含：未排班、休息、未到日期、请假、旷工、缺卡、迟到、早退、待打卡、正常（`Y9-result:15-26`）。

月报字段是 `clockInCount`、`clockOutCount`、`normalCount`、`lateCount`、`earlyCount`、`leaveDays`、`travelDays`、`absentDays`（`Y12-monthly:25-46`）。这是「计数 + 天数」口径，不按小时结算工资。

#### Odoo 与 Frappe 的口径

- Odoo `hr.attendance`：`worked_hours` 由 `check_out - check_in` 计算（`E3:210-218`）；`expected_hours = worked_hours - overtime_hours`（`E3:81-83`）；加班有 `overtime_hours`/`validated_overtime_hours` 两套值（`E3:46-51`）。Odoo 没有独立的「应出勤」列；`resource_calendar` 通过 `_get_employee_calendar` 参与工作时段与加班计算（`E3:205-233`）。
- Frappe `Attendance`：`working_hours`、`status`（Present/Absent/On Leave/Half Day/Work From Home）、`late_entry`、`early_exit`、`shift`、`standard_working_hours`、`actual_overtime_duration`（`F2`）。`Shift Type` 提供半日/缺勤阈值、迟到/早退宽限（`F5:81-120`）。

事实结论：固定班统计的最小输入是「班次 + 打卡 + 请假 + 节假日」；如果只有打卡没有班次，只能统计打卡次数和首末时间，不能算迟到/早退/旷工/应出勤。芋道 OA 模块的月报只有 `clockInCount`/`clockOutCount`/`normalCount`/`lateCount`/`earlyCount`/`leaveDays`/`travelDays`/`absentDays`（`Y12-monthly`），对应的是简单打卡口径；芋道 HRM 模块才有班次与分钟级扣减（`Y9`）。

### 3.6 考勤的可观察最小集

按「是否做固定班」「是否做假期余额」两个开关，事实上有三档：

1. **简单打卡**：`oa_attendance` 形状，字段 userId/type/status/attendanceTime/attendanceIp/remark，加月报计数（`Y12`、`Y12-monthly`）。没有班次、没有请假余额、没有审批联动。
2. **固定班 + 审批联动**：考勤组/班次（工作日、上下班、打卡窗口、休息段、特殊日期）+ 打卡事件 + 请假记录（类型、起止、天数、审批状态、流程实例）+ 日结果计算。芋道 HRM 的 `hrm_attendance_group`/`hrm_attendance_clock`/`hrm_attendance_leave` + 统计服务就是这一档（`Y5`、`Y6`、`Y7`、`Y9`、`Y10`）。这一档仍然没有假期余额。
3. **固定班 + 假期余额**：在第 2 档上增加假期类型、发放、流水/分配（Odoo/Frappe），并定义冻结（Odoo 的 `virtual_remaining_leaves`/`leaves_requested`）与结转/过期（`F6`、`F7`、`F9`、`E6`、`E7`）。

三档的共同字段交集是：员工/账号、日期、上班/下班或起止时间、状态、来源/备注。把「请假、加班、外出、出差」作为审批单还是考勤行，是三档之外的另一维选择；Frappe 选择写考勤行，芋道选择保留申请记录并在统计时读取（`F8`、`Y9`、`Y10`）。

- 最小报销单是「单头 + 明细 + 票据附件 + 审批状态/流程实例」。明细可以做成独立子表（Odoo/Frappe/Dolibarr），也可以做成单头 JSON（芋道）。JSON 方案的代价是没有独立明细 id、不能按明细行做外键/索引/生命周期；芋道的注释直接承认「明细随报销单保存，不维护独立编号及生命周期」（`Y13:99-107`）。
- 单头汇总字段有两种：派生（芋道 `invoiceCount`/`totalPrice` 由明细汇总）与独立存储（Odoo/Frappe/Dolibarr 单头合计列）。派生方案要求每次明细变更重算；独立存储要求事务内同步。
- `claimed` 与 `sanctioned` 是两套金额：Frappe 明细同时有 `amount` 与 `sanctioned_amount`，单头同时有 `total_claimed_amount`/`total_sanctioned_amount`（`F11:134-146`、`F11-detail:73-91`）；Odoo 没有「核定金额」字段，审批后直接形成 `total_amount`；芋道只有 `price`，没有核定金额（`Y13:136`）。

### 4.2 发票附件

中国税务规则的事实是：税前扣除凭证分为内部凭证和外部凭证；境内增值税应税项目且对方是已办理税务登记的增值税纳税人时，原则上以发票（含电子发票）作为税前扣除凭证；对方是无需税务登记的单位或小额零星经营个人时，可用代开发票或收款凭证加内部凭证；企业应把合同协议、支出依据、付款凭证留存备查；因对方注销等特殊原因无法补开、换开发票时，需要原因证明、合同/协议、非现金付款凭证等（`G2`）。该公告规定的是凭证种类与留存义务，没有规定系统字段；从凭证可证明性看，报销模型至少要能挂发票文件与合同/付款凭证，发票号/代码等属于可记录的元数据，不是该公告的字段要求。

三套实现的附件事实：

- Odoo `hr.expense` 有 `attachment_ids`（`One2many('ir.attachment')`）、`message_main_attachment_id`、`nb_attachment`；`same_receipt_expense_ids` 按附件 `checksum` 分组识别同一票据，`duplicate_expense_ids` 按员工/产品/日期/金额/币种等字段识别重复报销（`E8:77-111`、`E8:467-514`）。附件是通用 `ir.attachment`，不是报销行上的文件路径数组。
- Frappe `Expense Claim`/`Expense Claim Detail` 的 doctype JSON 中没有 `Attach`/`Attach Image` 字段（`F11`、`F11-detail`）；通用 `File` doctype 有 `attached_to_doctype`/`attached_to_name`/`attached_to_field` 与 `content_hash`（`F18`），报销单据可以通过它挂附件。事实是「本次读取的报销 doctype 没有附件字段」，不是「Frappe 不能传附件」。
- 芋道 `OaReimbursementDO` 只有 `fileUrls`（JSON 字符串数组）和 `invoiceCount`（票据张数），没有发票号、发票代码、开票日期、税额字段（`Y13:71-107`、`Y13:128-136`）。`oa_travel_reimbursement` 同样只有 `fileUrls` 与明细金额（`Y14:99-146`）。
- Dolibarr 明细有 `fk_ecm_files` 指向 ECM 文件，单头有 `model_pdf`/`last_main_doc`（`D1:55-63`、`D2:56`）。

本仓 `oa_attachment` 的字段是 `process_id`、`owner_user_id`、`draft_id`、`storage_id`、`object_key`、`temporary_object_key`、`file_name`、`content_type`、`size_bytes`、`status`、`upload_expires_at`（`R2:2-24`）；没有 `business_type`/`business_id`/`invoice_id`/`checksum`。它可以把发票附件绑定到一次审批（`process_id`），也能在提交前用 `draft_id` 暂存；但草稿态 `PENDING` 在 `pendingTtl`（默认 24 小时）后被清理（`R20:27`、`R19:230-252`），不能当长期档案库。若发票要独立于审批存在、要被多张报销单引用、要做重复检测，必须新增发票元数据表或给附件表加业务维度与 checksum。

### 4.3 金额精度与币种

| 实现 | 金额类型/精度 | 币种字段 | 汇率/公司币种 |
|---|---|---|---|
| Odoo 18 | 合计用 `fields.Monetary`；单价 `price_unit` 是 `fields.Float`（`E8:114-148`） | `currency_id`、`company_currency_id`（`E8:149-165`） | `currency_rate`；`tax_amount`/`total_amount` 分别有 `_currency` 与公司币种两套字段（`E8:114-166`） |
| Frappe HR | `Expense Claim`/Detail 的金额字段类型是 `Currency`（`F11:134-146`、`F11-detail:73-91`） | `currency`（`F11:410`） | `exchange_rate` + `base_total_*`/`base_grand_total`（`F11:422-450`） |
| 芋道 | Java `BigDecimal`，注释「单位：元」（`Y13:76-87`、`Y13:136`） | 无币种字段（`Y13:39-107`） | 无汇率字段 |
| Dolibarr | `double(24,8)`（`D1:25-29`、`D2:30-54`） | `multicurrency_code`（`D1:59`） | `multicurrency_tx`、`multicurrency_total_*`（`D1:58-63`、`D2:50-54`） |

事实结论：

- 四套实现都没有把金额存成整数分。Odoo/Frappe 用货币精度（Odoo 的 `res.currency.decimal_places` 由 `rounding` 推出，默认 `rounding=0.01`；`E10:39-41`、`E10:165-170`；Frappe 的 Currency doctype 有 `fraction_units`/`smallest_currency_fraction_value`，`F13`）；芋道用 `BigDecimal` 元；Dolibarr 用 `double(24,8)`。
- MySQL 手册明确 `DECIMAL`/`NUMERIC` 存精确值、适合货币，`FLOAT`/`DOUBLE` 是近似值，浮点比较和求和可能出现肉眼看不到的差异（`M1`、`M2`）。Dolibarr 的 `double(24,8)` 是「用近似类型存金额」的事实反例，不代表它适合作为本仓的精度依据。
- 单币种实现可以没有币种/汇率字段（芋道）；多币种实现必须至少有三组金额：原币金额、公司币种金额、汇率（Odoo/Frappe/Dolibarr）。如果本仓只做人民币报销，币种字段可以不存在；如果要做多币种，`form_values` 的 JSON 文本无法承担精度和汇总。

### 4.4 台账与统计

「台账」在实现里通常有两层：审批台账和支付台账。

- 审批台账：单据的审批状态、审批人、审批时间、流程实例。芋道 `oa_reimbursement.status` 是 BPM 状态，`OaReimbursementStatusListener` 在流程状态事件里回写业务行（`Y13-listener:17-29`）；Frappe `approval_status` 是审批状态，`status` 另外承载 Draft/Submitted/Rejected/Paid/Partially Paid/Unpaid/Cancelled（`F11:125`、`F11:282`）；Odoo `hr.expense.state` 与 sheet `state` 分开（`E8:85-99`、`E9:62-76`）。
- 支付台账：Frappe 有 `is_paid`、`total_amount_reimbursed`、`clearance_date`、`total_advance_amount`（`F11:159-319`）；Odoo 有 sheet `payment_state`、`amount_residual`、`account_move_ids`（`E9:146-211`）；Dolibarr 的 `fk_statut=6` 表示 paid，另有 `fk_bank_account`（`D1:46-63`）；芋道 `oa_reimbursement` 没有支付状态/时间/凭证，只有审批状态；`oa_travel_reimbursement` 有 `payStatus`（`Y14:78-82`）。

统计口径的事实差异：

- 芋道报销单头 `invoiceCount`/`totalPrice` 是明细汇总，注释明确「不由用户单独填写」（`Y13:71-87`）；本次读取的 reimbursement service/controller 目录没有按部门/费用类型的汇总表，列表分页查询直接读单头（`Y13-service`）。
- Frappe 单头同时有 claimed/sanctioned/grand total/advance amount，能直接做「申请金额、核定金额、已报销金额」三列台账（`F11:134-346`）。
- Odoo 把报销行汇总到 sheet，再由 sheet 生成 `account_move_ids`；台账的最终金额在会计凭证上（`E9:199-211`）。
- Dolibarr 单头 `total_ht`/`total_tva`/`total_ttc` 与状态、银行账户一起构成财务台账（`D1:25-63`）。

### 4.5 与审批模板的关系

芋道的做法是「业务表 + BPM 流程定义 + 状态监听器」：

- `OaReimbursementServiceImpl.submitReimbursement` 把业务行状态置为 RUNNING，调用 `processInstanceApi.createProcessInstance`，`processDefinitionKey = BpmModelConstants.REIMBURSEMENT`（值为 `oa_reimbursement`），`businessKey = reimbursement.id`，变量里带 `totalPrice`（`Y13-service:79-93`、`Y16:13`）。
- `OaReimbursementStatusListener` 继承 `BpmProcessInstanceStatusEventListener`，按流程定义 key 过滤，在事件里用 `event.getBusinessKey()` 找到业务行并更新 `status`（`Y13-listener:17-29`）。
- 请假同理：`HrmAttendanceLeaveServiceImpl` 用 `LEAVE_PROCESS_KEY = "hrm_attendance_leave"`，`businessKey = attendanceLeave.id`，监听器回写 `approvalStatus`/`approvalTime`/`approvalReason`（`Y10:47`、`Y10:87-93`、`Y10:27-31`）。

本仓的做法是「审批账本 `oa_process` + 通用模板」：

- `oa_process` 有 `process_code`、`user_id`、`process_template_id`、`process_type_id`、`title`、`description`、`form_values`、`process_instance_id`、`current_auditor`、`status`、`idempotency_key`（`V1:124-140`、`R11:17-59`、`V105`）。`status` 的语义是 0 默认、1 审批中、2 通过、-1 拒绝（`R11:53-55`、`R16:34-47`）。
- `ApprovalWriter.startUp` 把 `form_values` 原样存 `oa_process`，把 `String.valueOf(process.getId())` 作为 Flowable businessKey，把 `formData` 作为引擎变量 `data`（`R14:92-110`、`R15:154-157`）。
- 模板的 `form_props` 是 form-create JSON，服务端只做「结构合法 + `$required` 必填存在」校验，不做类型/范围/金额精度校验（`R15:38-49`、`R15:51-140`、`R14:176-184`）。`form_values` 是 `TEXT`（`V1:132`），没有金额列、日期列、员工列，不能直接做台账/统计查询。
- 模板发布有独立证据表 `oa_process_template_publication`：`process_template_id` 唯一、`artifact_path`、`artifact_sha256`、`process_definition_key`、`deployment_id`、`process_definition_id`（`V4:3-15`）；发布时写证据并把模板状态置 1（`R17:110-141`）；发起时要求已发布且证据校验通过（`R17:192-205`、`R18:8-19`）。已发布模板不能再保存/删除（`R17:96-107`、`R17:145-154`），表单结构变更需要新模板。

事实结论：

- 如果业务单只依赖 `oa_process.form_values`，审批能跑，但没有 typed 业务表就无法做「按员工/部门/费用类型/日期」的台账和统计。芋道的每张业务单都有自己的 typed 列（`Y13:39-107`、`Y15`），这是它能做列表筛选和监听回写的前提。
- 如果业务表存 `process_id` 指向 `oa_process`，它与本仓 Flowable businessKey 一致（businessKey 就是 `oa_process.id`）；如果业务表存自己的 id 并想让它当 businessKey，需要在 `ApprovalWriter` 发起前先插入业务行并改传参，当前代码没有这个分支（`R14:100-110`）。
- 本仓 `oa_process` 没有 `business_type`/`business_id` 列（`V1:124-140`）；业务表只能反向存 `process_id` 或 `process_instance_id`。两种方向都能建立关联，但一个是「审批账本找业务」，一个是「业务找审批账本」，查询路径不同。

### 4.6 不做预算、借款、对公付款时的边界

- **预算**：本次读取的四套报销模型都没有预算表/预算校验字段。Odoo/Frappe 有 `account_id`、`cost_center`、`project` 等归集维度（`E8:181-198`、`F11:250-260`），但它们是会计/成本归集，不是预算额度控制。省略预算时，报销单仍然可以按费用类型/部门/项目归集。
- **借款**：Frappe 有 `Employee Advance` doctype 与 `Expense Claim.advances` 子表、`total_advance_amount`（`F11:319`、`F-advance`）；Odoo 用 `payment_mode` 区分「员工垫付/公司支付」（`E8:170-180`），没有独立的员工借款单；芋道报销单没有借款字段（`Y13:39-107`）。省略借款时，`total_advance_amount`/`advances` 整块可以不存在，报销金额就是应报销金额。
- **对公付款**：Odoo 通过 `hr.expense.sheet` 的 `payment_state`/`account_move_ids` 进入会计付款（`E9:167-211`）；Frappe 有 `payable_account`、`mode_of_payment`、`is_paid`、`clearance_date`、`total_amount_reimbursed`（`F11:159-260`）；Dolibarr 有 `fk_bank_account` 和 `fk_statut=6`（`D1:46-63`）。芋道 `oa_reimbursement` 没有这些字段，只有审批状态；`oa_travel_reimbursement` 只有 `payStatus` 布尔（`Y14:78-82`）。省略对公付款时，审批通过只是「同意报销」，不产生付款凭证/银行流水/会计凭证。

事实结论：不做预算/借款/对公付款，报销模型可以缩到「审批单 + 明细 + 票据附件」；一旦要做其中任一项，就需要额外的额度表、借款核销表或付款/会计表，不能只靠单头 `status` 表达。

## 6. 对三张域决策票的事实输入

### 6.1 #273 人事档案

- 字段集的最小四块是主档、任职、合同、离职；异动是第五块。三套实现的字段清单见 2.1/2.3（`E1`、`E2`、`F1`、`Y1`-`Y4`）。
- 账号边界的事实是：员工可以没有账号，账号可以没有员工；`sys_user` 只覆盖登录身份，不覆盖人事档案（2.2）。
- 合同到期提醒的最小输入是结束日期 + 提醒窗口 + 调度器 + 提醒出口；Odoo 有完整扫描逻辑（`E2:168-180`），Frappe 只有 `contract_end_date` 与通知期字段、没有提醒任务/窗口（`F1:335-342`），芋道有 `expireRemind` 标记与首页到期人数统计（`Y2:92`、`Y-contract:29-41`、`Y-contract-home:418-424`），但没有到期扫描 Job（`Y-job`）。
- 本仓可复用的是账号/组织/岗位/权限/审批/附件/定时任务；必须新增的是员工、合同、异动、离职四组表，以及员工档案附件（5.2）。

### 6.2 #274 考勤

- 固定班的最小形状是「组 + 班次（工作日/上下班/打卡窗口/休息段/特殊日期）」；芋道给了一个可直接对照的 JSON 形状（`Y5:79-186`），Frappe 是 `Shift Type` + `Shift Assignment`（`F5`），Odoo 是 `resource.calendar`（`E4`）。
- 打卡事件与补卡是两件事：打卡是事件表（`Y6`、`F3`、`E3`），补卡在 Frappe 是 `Attendance Request`（`F4`），芋道没有独立补卡单（`Y-controller`）。
- 假期余额需要类型/发放/流水；Odoo 用 allocation + leave 计算并区分 requested/approved/taken（`E6`、`E7:485-525`），Frappe 用 allocation + ledger（`F7`、`F9`），芋道只有 leave 记录（`Y7`）。
- 审批通过后的写入有三条事实路径：Frappe 写 Attendance 行（`F8:300-364`），Odoo 写 `resource.calendar.leaves`（`E5:909-926`），芋道回写审批状态并在统计时扣减（`Y10`、`Y9`）。
- 统计口径的最小输入是「班次 + 打卡 + 请假 + 节假日」；芋道日结果枚举与月报字段给出了具体指标（`Y9-result`、`Y12-monthly`），Odoo/Frappe 给出工时/迟到/早退字段（`E3`、`F2`）。

### 6.3 #275 报销

- 最小模型是「单头 + 明细 + 票据附件 + 审批状态/流程实例」；芋道用 JSON 明细，Frappe/Odoo/Dolibarr 用独立行表（4.1）。
- 发票附件在 Odoo 走通用 `ir.attachment` 并有 checksum（`E8:77-111`），芋道只有 `fileUrls`/`invoiceCount`（`Y13`），本仓 `oa_attachment` 只能绑审批且无发票元数据（5.3）。
- 金额精度的事实是：MySQL `DECIMAL` 精确、`FLOAT`/`DOUBLE` 近似（`M1`、`M2`）；Odoo/Frappe 用货币精度（`E10`、`F13`），Dolibarr 用 `double(24,8)`（`D1`），芋道用 `BigDecimal` 元且无币种（`Y13`）。
- 台账分为审批台账与支付台账；芋道报销单只有审批状态，Frappe/Odoo/Dolibarr 有支付/会计字段（4.4）。
- 不做预算/借款/对公付款时，模型可以缩到审批单；要做任一项，必须新增额度、借款核销或付款/会计表（4.6）。
