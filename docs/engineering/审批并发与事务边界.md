# 审批并发与事务边界

## 审批写入

`OaProcessServiceImpl.startUp` 和 `approve` 都由 Spring `@Transactional` 包围。发起时先写 `oa_process`，再启动 Flowable 流程并写审批记录；审批时先完成 Flowable task，再写 `oa_process_record` 和更新 `oa_process`。当前应用的 Flowable Spring 引擎与 MyBatis 使用同一个应用数据源，因此这些同步数据库写入在同一个 Spring 事务中提交或回滚。

`ApprovalContractTest.startUpRollsBackBusinessFlowableAndSynchronousCarbonCopyWritesTogether` 在 `TASK_CREATED` 上注册测试监听器，让它向同一个数据源写入一条抄送探针记录；随后通过业务审批记录的约束制造失败。测试验证业务行、Flowable 运行表和历史表、以及监听器写入都随外层事务回滚。该探针只验证 Flowable 同步事件回调的事务接缝；当前 checkout 尚无正式抄送模块，真实模块由 #93 实现。

事务边界只覆盖同步加入当前数据源事务的写入。抄送监听器若改用异步执行或 `REQUIRES_NEW`，便不属于这次审批事务。监听器的错误是否中止审批还由 `isFailOnException()` 决定；将其设为 `false` 会吞掉监听器异常，不等同于关闭成功写入的事务参与。

## 同一任务的并发审批

`ApprovalContractTest.concurrentApprovalRequestsForSameTaskHaveExactlyOneCommittedWinner` 将两个请求放在同步点后一并提交同一 task，重复三轮。每轮只有一个 Flowable 操作成功；另一个请求以 Flowable 异常失败。合同断言还检查：审批记录只增加一条、原审批人不再有待处理任务、下一审批人获得待处理任务。这锁定的是公开 `Approval.approve` 的并发行为，不依赖进程内互斥锁。

## Redis 权限缓存

`IndexController.info` 用用户名作为 Redis key 写入权限 JSON。角色分配只影响目标用户；角色信息或菜单权限变化影响该角色成员；菜单新增、编辑、删除还会影响管理员的全量菜单权限。`PermissionCacheInvalidator` 在数据库事务提交后删除这些用户对应的 Redis key；事务回滚时不清除仍与数据库一致的缓存。菜单分配按该角色现有成员失效，未受影响角色的缓存保留。
